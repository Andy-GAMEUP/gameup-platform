## 1. 게임 등록 & 심사

### 1.1 상태 값 정의

게임은 **서비스 상태(status)**와 **심사 상태(approvalStatus)** 두 가지가 독립적으로 관리됩니다.

#### 서비스 상태 (status)

| 값 | 의미 |
|----|------|
| `draft` | 임시저장 / 심사 전 / 강제중지 상태 |
| `beta` | 베타 서비스 중 |
| `published` | 정식 출시 중 |
| `archived` | 서비스 종료 |

#### 심사 상태 (approvalStatus)

| 값 | 의미 |
|----|------|
| `not_submitted` | 심사 미신청 (최초 등록 후 기본값) |
| `pending` | 심사 요청됨 (관리자 검토 대기) |
| `review` | 관리자가 검토 중 |
| `approved` | 심사 승인됨 |
| `rejected` | 심사 거부됨 |

#### 서비스 유형 (serviceType)

| 값 | 의미 |
|----|------|
| `beta` | 베타 테스트 서비스 |
| `live` | 정식 라이브 서비스 |
| `review` | 심사 중 (재심사 요청 시) |
| `ended` | 종료됨 |

---

### 1.2 게임 등록 흐름

```
개발자 등록
  ↓
status=draft / approvalStatus=not_submitted  (기본값)
  ↓
gameDomain(게임 URL) 입력 필수
  ↓
심사 요청 (requestReview)
  ↓
approvalStatus=pending
  ↓
관리자 검토 중으로 변경 가능
  ↓
approvalStatus=review
  ↓
[승인] approvalStatus=approved → status=beta로 오픈 (또는 기존 status 유지)
[거부] approvalStatus=rejected + rejectionReason 저장
```

**심사 요청 조건:**
- `gameDomain`(게임 URL)이 반드시 입력되어 있어야 함
- 이미 `pending` 또는 `review` 상태이면 중복 요청 불가
- 유효한 URL 형식이어야 함 (예: `https://mygame.com`)

**출시(published) 전환 조건:**
- `approvalStatus === 'approved'`인 경우에만 `status=published`로 변경 가능
- 승인되지 않은 상태에서 published 시도 → 400 오류

---

### 1.3 게임 수정 규칙

#### 출시 중인 게임 (status=published)
- serviceType(베타/라이브)에 무관하게 수정 시 **즉시 반영**, 재심사 없음
- 수정 가능 필드: title, description, genre, thumbnail, bannerImage, trailer, website, discord, notes, platform, engine, startDate, endDate, maxTesters, testType, requirements, gameDomain, monetization

#### serviceType(베타↔라이브) 변경 시
- `approvalStatus`가 `not_submitted`으로 자동 리셋
- `status`가 `published`가 아닌 경우 → `draft`로 변경
- **재심사 필요**

#### 편집 잠금 조건
- `status !== 'published'` && (`approvalStatus === 'pending'` 또는 `'review'`): 심사 진행 중 편집 불가 (UI 레벨)
- `status !== 'published'` && `approvalStatus === 'approved'`: 출시 대기 중 편집 불가

### 1.4 관리자의 게임 상태 제어

- **게임 "강제 중지" 기능은 플랫폼 전체에서 완전히 제거됨** (`suspend`/`reactivate` 액션 자체가 백엔드에 없음). 게임을 멈추는 유일한 방법은 삭제 또는 아카이브(종료)뿐
- 게임 관리(`/admin/games`) 목록의 "강제 중지" 버튼은 삭제로 대체됨 — 클릭 시 사유 입력 대신 "개발사와 충분히 논의하셨습니까?" 경고와 게임명 입력 확인(`DeleteGameModal`)을 거쳐 개발자 셀프 삭제와 동일한 경로(`DELETE /api/games/:id`)로 즉시 영구 삭제 처리됨 (1.5 참고, 삭제 게임 관리에 기록됨)
- 분석/지표 상세 화면(`AdminGameMetricsPage.tsx`)의 "중지"/"재활성화" 버튼도 함께 제거됨. "아카이브"(서비스 종료)만 남아있음:

| 액션 | 동작 | 설명 |
|------|------|------|
| `archive` (서비스 종료) | status=archived | archiveReason 기록됨 |
| `set_beta` | status=beta | |
| `set_published` | status=published | |

- `suspendedAt`/`suspendReason`/`statusBeforeSuspend` 필드는 과거 기록 호환을 위해 DB 스키마에는 남아있지만, 이 값을 새로 설정하는 코드는 어디에도 없음 (죽은 필드)

### 1.5 게임 삭제 & 복구

- **2026-08-20부터 소프트 삭제로 전환**: 게임 삭제는 `Game` 문서를 실제로 지우지 않고 `isDeleted: true` 플래그만 표시한다 (파일도 그대로 둔다, `uploads/deleted/` 이동 없음)
- `GameDeletionLog`에 삭제자 정보, 게임 스냅샷, IP, UserAgent는 감사 기록용으로 계속 남긴다
- **삭제해도 커뮤니티 탭/게시물은 그대로 유지된다** — 커뮤니티 사이드바(베타/라이브 게임 목록)는 `includeDeleted=true`로 조회해서 삭제된 게임도 계속 탭에 노출하고, 새 글 작성도 계속 가능하다. 반대로 게임 스토어 목록(`MainPage`), 플레이 상세페이지(`/games/:id`), 개발사 게임관리 목록, 관리자 게임관리 목록은 전부 `isDeleted: true`인 게임을 제외해서 안 보인다
- **복구 가능**: 관리자가 삭제 로그에서 복구하면 `isDeleted` 플래그만 해제된다 (문서를 다시 만드는 게 아니므로 파일 이동도 필요 없음). 복구 시 `restoredAt` 타임스탬프 기록
- **커뮤니티 탭 수동 숨김**: "삭제 게임 관리"(`/admin/game-deletion-logs`) 목록의 "커뮤니티 탭" 토글로, 소프트 삭제된 게임의 커뮤니티 사이드바 노출을 관리자가 수동으로 끌 수 있다 (`Game.hiddenFromCommunity`). 끄면 스토어/사이드바 어디서도 안 보이고, 그 게임을 즐겨찾기(북마크)해뒀던 유저의 "내 커뮤니티" 목록에서도 같이 사라진다. 다시 켜면 즉시 복원된다. 게임 자체가 완전 삭제(과거 하드 삭제 로그)된 경우엔 토글 대상이 아니다
- 2026-08-20 이전에 삭제된 게임은 기존 방식(하드 삭제)이라 이 규칙이 소급 적용되지 않는다 — 그 로그들은 여전히 스냅샷 재생성 방식으로만 복구된다 (`restoreGame`이 두 방식을 자동 분기 처리)

**게임 삭제 시 커뮤니티 탭 종료 공지 프로세스 (운영 정책, 시스템이 자동으로 강제하지 않음 — 관리자가 직접 수행)**

게임을 삭제해도 커뮤니티 탭은 곧바로 사라지지 않고 계속 노출되므로(위 내용 참고), 관리자가 실제로 탭을 숨기기(`hiddenFromCommunity`) 전에 아래 절차를 거친다:

1. 관리자가 해당 게임을 삭제한다.
2. 관리자가 **커뮤니티 공지(플랫폼 공지 또는 해당 게임 공지)**로 아래 내용을 안내한다:
   - 게임 계약 종료 등 삭제 사유
   - "OO월 OO일 이후 이 게임의 커뮤니티 탭이 사라집니다" — 탭이 실제로 사라지는 예정일 명시
   - 남기고 싶은 글이 있으면 예정일 전에 다른 탭(자유게시판 등)으로 직접 옮겨달라는 안내
3. 예정일이 지나면 관리자가 "삭제 게임 관리"(`/admin/game-deletion-logs`) 목록에서 해당 게임의 "커뮤니티 탭" 토글을 꺼서(숨김) 실제로 탭을 없앤다.

공지 작성·예정일 도래 확인·토글 시점은 전부 관리자 재량으로 수동 처리한다 — 공지 등록 시 자동으로 탭이 숨겨지거나, 예정일이 되면 자동으로 숨겨지는 기능은 없다.
- **운영 중(`status: 'published'`) 게임은 개발사가 직접 삭제 불가** (서버에서도 차단, `게임 영구 삭제` 버튼도 미노출) — 운영 중인 게임 삭제는 관리자만 게임 관리 목록에서 가능
- 운영 전(베타/출시 대기 등) 상태에서는 개발사 게임관리 화면 상단 액션바("게임 출시" 버튼 왼쪽)에 삭제 버튼 노출

### 1.6 등급 분류 (ratingCertificate)

| 등급 | 값 |
|------|----|
| 전체이용가 | `전체이용가` |
| 12세 이용가 | `12세이용가` |
| 15세 이용가 | `15세이용가` |
| 청소년이용불가 | `청소년이용불가` |

- 인증번호, 인증일, 인증서 파일(PDF 등) 업로드 가능
- 별도의 인증서 검토 절차는 없음 — 관리자가 게임 심사를 승인(`approveGame`, action: 'approve')하는 순간 `ratingCertificate.isVerified`도 함께 `true`로 자동 처리됨
- `isVerified`가 `true`이고 `ratingClass`가 있어야 플레이어 게임 상세 페이지(`PlayerGameDetailPage.tsx`)에 등급 배지(`GracRatingBadge`)가 노출됨
- **`18세이용가`는 2026-08-26에 제거됨** — `청소년이용불가` 배지가 표시 텍스트 "19"(빨간색)로 그 역할을 겸한다. 기존 DB에 `18세이용가`로 저장된 게임은 없음(확인 완료).

### 1.7 게임 리뷰 관리 (2026-08-20 개편 — 관리자 → 개발자 이관)

- **게임 리뷰 차단/삭제는 더 이상 관리자 전용 기능이 아니다.** 각 개발사가 자신의 게임관리 화면(`GameDetailManagementPage.tsx`)의 "리뷰 관리" 탭("공지 작성" 오른쪽)에서 직접 관리한다
- 기존 관리자 콘텐츠 관리(`/admin/community?tab=reviews`)의 "게임 리뷰 관리" 탭은 완전히 삭제됨 (사이드바 메뉴 항목 포함)
- 백엔드도 게임 단위로 스코프 이전: `GET /api/games/:gameId/reviews/manage`, `PATCH /api/games/:gameId/reviews/:reviewId/block`, `DELETE /api/games/:gameId/reviews/:reviewId` — `requireRole('developer', 'admin')` + 게임 소유자 본인 확인(관리자는 예외적으로 모든 게임 접근 가능)
- 기존 전역 관리자 엔드포인트(`GET/PATCH/DELETE /api/admin/reviews`)는 제거됨

**⚠️ 미결 사항 (2026-09-03 발견)**: 리뷰 작성 폼(`PlayerGameDetailPage.tsx`)에서 제목(title)과 함께 유형(일반/버그/제안/칭찬) 선택 UI도 이미 제거된 상태였다 — 즉 새로 작성/수정되는 리뷰는 `feedbackType`이 항상 기본값 `'general'`로만 저장된다. 이번엔 우선 플레이어 화면(내 리뷰 표시, 리뷰 목록)에서 `feedbackType === 'general'`일 때 "일반" 배지만 안 보이게 숨겼다(과거에 실제로 bug/suggestion/praise로 저장된 리뷰의 배지는 그대로 유지).
- **아직 손대지 않은 것들**: `Review` 스키마의 `feedbackType`/`bugSeverity` 필드, `GameReviewManager.tsx`(개발자 리뷰관리 화면)의 유형 라벨/필터, `AdminGameMetricsPage.tsx`의 "피드백 유형 분포"/"버그 심각도 분포" 차트와 이를 만드는 `adminController.ts`의 집계 API(`feedbackTypes`, `bugSeverityDist`) — 전부 유형 선택 UI가 있던 시절 데이터에 의존한다.
- 앞으로 유형 선택 UI 없이 리뷰가 계속 쌓이면 위 차트/필터는 전부 "일반 100%"로 무의미해진다. **전체 제거(스키마 필드 포함) vs 유형 선택 UI만 복원 — 아직 결정 안 됨, 다음에 다룰 때 먼저 사용자에게 확인할 것.**

### 1.8 게임 목록 필터 — "내 게임" 태그 (2026-08-27 신설)

- 라이브존(`LiveGamesPage.tsx`)과 베타존(`BetazonePage.tsx`)의 장르 필터 태그 목록에 "전체" 바로 다음 위치("전체" ↔ 나머지 장르 태그 사이)에 "내 게임" 태그가 있다.
- **판정 기준: 이 계정으로 해당 게임의 "게임 시작" 버튼을 눌러본 적이 있는지** — 즐겨찾기(하트/북마크)나 리뷰 작성 여부와는 무관하다.
  - 게임 상세 페이지(`PlayerGameDetailPage.tsx`)의 "게임 시작" CTA를 클릭해야만 `POST /api/games/:gameId/play` 호출로 `PlayerActivity`(`type: 'play'`)에 기록된다. 상세 페이지에 그냥 들어가기만 해서는(구경만 해도) 기록되지 않는다.
  - 비로그인 상태에서 "게임 시작"을 클릭하면 로그인 페이지로 이동할 뿐 기록되지 않는다.
- "내 게임" 클릭 시 `GET /api/player/played-games`로 로그인 유저의 플레이 기록(`type: 'play'`) 게임 ID를 중복 제거해 가져오고, `GET /api/games?ids=...`로 현재 화면의 `serviceType`(라이브존은 `live`, 베타존은 `beta`)에 맞는 게임만 필터링해서 보여준다.
  - **라이브존/베타존은 서로 독립적이다** — 라이브존에서 플레이한 게임은 베타존의 "내 게임"에는 뜨지 않고, 그 반대도 마찬가지다(각 화면이 자기 `serviceType`만 조회하기 때문).
- 비로그인 상태에서 "내 게임" 태그를 클릭하면 `/login`으로 이동한다(다른 플레이어 전용 액션과 동일한 패턴, 알림 팝업 없음).
- **"내 게임"은 장르 태그와 배타적 선택이다** — 장르 태그(전체/RPG/액션 등)와 "내 게임" 중 항상 하나만 활성화된다. 장르를 클릭하면 "내 게임"이 꺼지고, "내 게임"을 클릭하면 장르 선택이 "전체"로 리셋된다. 두 개가 동시에 활성화 표시되지 않는다.
- 라이브존/베타존은 카드 레이아웃뿐 아니라 이런 필터 기능도 항상 동일하게 유지한다 — 한쪽에만 추가/수정하지 않는다(`docs/game-card-consistency-rule.md` 참고).

### 1.9 플레이 타임(세션 지속시간)은 수집 안 함 — 보류 결정(2026-09-08)

- `PlayerActivity` 스키마에 `sessionDuration` 필드가 있고, 저장용 API(`PATCH /games/:gameId/play/session`)와 프론트 계산 로직(`PlayerGameDetailPage.tsx`의 `handleStopPlay`)까지 이미 만들어져 있지만, **`handleStopPlay`를 호출하는 곳이 어디에도 없어서 실제로는 항상 비어있다.**
- **구조적으로 정확히 잴 방법이 없어서 보류함**: "게임 시작" 버튼은 `window.open(url, '_blank', 'noopener,noreferrer')`로 완전히 새 탭을 열어 게임을 실행한다(대부분 개발사의 외부 도메인). `noopener` 때문에 GameUp 탭과 게임 탭 사이에 JS 연결이 원천 차단되어, GameUp 페이지는 유저가 게임을 얼마나 했는지·언제 껐는지 알 방법이 없다 — GameUp 탭 자체의 생존 여부는 실제 플레이 여부와 무관.
- 실제로 재려면 둘 중 하나가 필요: ① 게임(외부 서버)이 직접 GameUp에 플레이 시간을 보고(기존 게임 포인트 연동 API 재활용, 개발사 협조 필수) ② 새 탭 대신 iframe으로 내장(많은 게임 호스팅이 iframe 삽입 자체를 막아둬서 전체 적용 불가, 구조 변경 큼). 둘 다 지금 범위 밖이라 보류.
- "플레이 여부"(1.8의 "내 게임" 판정)와는 별개다 — 플레이 "했는지 안 했는지"는 위 방식으로 정상 기록되고, 안 되는 건 "얼마나 오래 했는지"뿐이다.

### 1.10 베타존 게임 등록 간소화 (2026-09-10 신설 — 정책 확정, 시스템 반영은 대기)

**⚠️ 이 절은 방향성/정책만 먼저 확정한 상태다. 실제 등록 폼·백엔드 검증 로직은 아직 이 규칙에 맞춰 수정되지 않았다 — "뉴플레이 챌린지" API 개발이 끝나는 대로 코드를 함께 수정·보완할 예정이니, 다음에 이 영역을 다룰 때는 이 절부터 먼저 확인할 것.**

**목적**: 기존 베타존 업로드 방식을 전면 개편해 등록 절차를 간소화한다. 개발사가 부담스러워하는 항목(스크린샷 제작, 게등위 등급 획득)을 없애서, 많은 개발사가 부담 없이 대량으로 베타 게임을 등록하게 하고 베타존 콘텐츠 분량을 늘리는 것이 목표다.

**간소화 내용**:
- 베타존 게임 등록 시 **스크린샷 제작**과 **게등위(게임물관리위원회) 등급 획득**을 요구하지 않는다 — 이 두 항목이 개발사 입장에서 가장 어렵고 부담스러운 절차였음.

**기본 규칙**:
- 베타존 진행 기간: 최대 60일
- 참여 인원: 최대 1만 명
- 진행 방식: **선착순 즉시 확정** — 유저가 "베타존 신청" 버튼을 누르면 별도 관리자 승인 절차 없이 바로 확정된다(2026-09-15 확정, §1.12a 참고)

**무료 진행 필수**:
- 베타존 게임은 반드시 무료로 진행한다.
- 이는 게등위 등급 심사를 받지 않고 서비스할 수 있는 최소 조건이기 때문 — 즉 "게등위 등급 면제"는 "무료 게임"이라는 전제 위에서만 성립한다.

**참여 유저 보상**:
- 참여 유저에게 캐시를 지급하는 방식이 이상적이나, **일단 캐시 지급은 하지 않는다.**
- 대신 "뉴플레이 챌린지"를 지급하고, 해당 베타 게임이 정식 출시(라이브 전환)할 때 그 챌린지를 사용할 수 있게 한다.
- **뉴플레이 챌린지 지급/사용 관련 API가 아직 개발 완료되지 않았다** — 그래서 세부 동작(지급 시점, 수량, 사용 조건 등)은 아직 정해지지 않았고, 해당 API 개발이 끝나면 그때 디테일을 다시 논의해서 이 절을 구체화한다. 지금은 방향성만 규칙으로 기록해둔 상태다.

### 1.11 메인페이지 베타존/라이브존 순위 (2026-09-11 신설)

**목적**: 메인페이지 "라이브존"/"베타존" 순위(각 5개)는 기존엔 그냥 최신 등록순이던 더미였는데, 실제 인기/매출 기준 순위로 교체했다. 계산 코드는 `apps/api/src/jobs/updateZoneRankings.ts`.

**라이브존 — 최근 7일 매출 기준**:
```
revenue(game) = Σ amount   (Payment.status = 'completed' AND Payment.createdAt ≥ 오늘 − 7일 AND Payment.gameId = game)
```
- 매출 내림차순 정렬, 매출 데이터가 없는 게임은 0원으로 취급되어 순위 뒤로 밀림

**베타존 — 매출이 없는(출시 전) 게임이라 아래 4개 지표를 가중합산**:
```
score(game) = 0.45 × pctRank(playRate)
            + 0.30 × pctRank(bayesianRating)
            + 0.15 × pctRank(reviewCount)
            + 0.10 × pctRank(communityCount)
```
- 가중치(0.45/0.30/0.15/0.10)는 `apps/api/src/jobs/updateZoneRankings.ts`의 `BETA_WEIGHTS` 상수 하나만 고치면 조정 가능
- 리뷰 수/커뮤니티 게시물 수는 악플·논쟁으로도 부풀려질 수 있어(신뢰도가 낮음) 플레이 달성률·평점보다 낮은 비중만 부여(2026-09-11)

**① 플레이 달성률(playRate)** — 플레이 수를 그대로 쓰면 게임마다 목표로 하는 최대 유저 수가 달라 비교가 불공정해서, 목표 테스터 수 대비 달성률로 정규화:
```
playRate(game) = playCount ÷ (maxTesters > 0 ? maxTesters : 10000)
```
- `maxTesters`(목표 테스터 수)를 설정하지 않은 게임(0)은 플랫폼 기본 상한(§1.10 "참여 인원 최대 1만 명")을 목표로 간주

**② 베이지안 보정 평점(bayesianRating)** — 리뷰 1~2개짜리 만점 게임이 리뷰 수백 개 쌓인 4점대 게임을 이기지 못하도록 보정:
```
globalAvg = 리뷰 1개 이상인 베타 게임들의 평균 rating   (그런 게임이 없으면 3점 = 5점 척도 중간값)
m = 10   (BETA_RATING_MIN_VOTES — 신뢰 기준선)
bayesianRating(game) = (reviewCount / (reviewCount + m)) × rating + (m / (reviewCount + m)) × globalAvg
```
- 리뷰가 0개인 게임은 `bayesianRating ≈ globalAvg`(중립값)로 수렴, 리뷰가 많이 쌓일수록 실제 평점(`rating`)에 가까워짐

**③ 지표 정규화 — 백분위 순위(pctRank)** — min-max 정규화는 극단값 하나(예: 게시물 수가 압도적인 게임 하나) 때문에 나머지 게임들 점수 차이가 다 뭉개지는 문제가 있어서, 순서(백분위)만 보는 방식으로 대체:
```
pctRank(x, 그 지표의 전체 베타 게임 값 배열) = (x보다 작은 값의 개수 + 동점 그룹 내 평균 순위 보정) / (게임 수 − 1)
```
- 결과는 항상 0~1 사이, 동점은 평균 순위를 나눠 가짐 (구현: `percentileRank()` 함수)

**갱신 주기**: 실시간이 아니라 **매일 오전 9시(KST)** 배치로 재계산한다 (`apps/api/src/jobs/updateZoneRankings.ts`, 서버 시작 시 1회 즉시 실행 + 이후 매일 09:00 KST). 계산 결과는 `GameRanking` 컬렉션(zone별 rank/score)에 저장해두고, 프론트는 `/api/games/rankings?zone=beta|live` 조회 시 이 캐시된 값만 읽는다 — 매 요청마다 실시간 재계산하지 않는다.

**참고**: `serviceType`이 바뀌거나(라이브 전환 등) 게임이 언퍼블리시/삭제되면 다음 09:00 배치에서 자동으로 순위 컬렉션에서 제외된다(실시간 반영 아님, 최대 하루 지연).

### 1.12 메인페이지 "베타존 추천" 배너 — 게임 아이콘 자동 표시 (2026-09-11 신설)

**목적**: 메인페이지 옛 "신작 게임" 자리를 대체 — 관리자가 배너 이미지를 직접 만들어 올리는 대신, **베타존 게임을 선택하기만 하면** 그 게임의 아이콘(썸네일)·이름·모집 현황이 자동으로 표시된다.

- 서버는 배너의 `linkUrl`(`/games/:id` 형식)에서 게임 id를 뽑아 그 게임의 `thumbnail`을 `imageUrl`로 자동 저장한다(`useGameIcon` 플래그로만 동작 — 다른 배너 종류는 항상 직접 올린 이미지를 그대로 씀, 절대 자동 대체 안 됨).

- **"등록 유저 수"**는 `Game.testers` 필드, **"모집 완료"** 전환 기준은 `Game.testers ≥ Game.maxTesters`(단, `maxTesters`가 0/미설정이면 모집 완료 전환 안 함).

### 1.12a 베타 테스터 모집/확정 (2026-09-14~15 구현 완료)

**방식**: §1.10에서 명시한 대로 **선착순 즉시 확정**이다. 신청 = 확정이며 별도 승인/거절 상태가 없다 — `GameTesterApplication` 모델(레코드 존재 자체가 확정을 의미)에 그렇게 설계돼 있고, 2026-09-15 사용자 확인으로 최종 확정됐다. - 제외 시 `Game.testers` -1
- 개발자 콘솔의 옛 "테스터 관리" 메뉴(`TesterManagementPage.tsx`, 100% 목업 데이터)는 이 화면으로 대체되어 삭제됨

### 1.12b 베타존 리뷰/Q&A 작성 가능 시점 (2026-09-17 신설)

베타존 게임(`serviceType='beta'`)에서 리뷰/개발사 Q&A를 작성하려면 **베타존 신청(`hasApplied`) + 테스트 시작일(`startDate`) 경과** 두 조건이 모두 충족돼야 한다. 신청만 하고 테스트 시작 전이면 버튼/입력창은 화면에 보이되 비활성화 처리하고, "테스트 시작일(YYYY. M. D.)부터 작성 가능합니다" 안내를 보여준다 — 조건 미충족 시 버튼을 아예 숨기지 않는다.

- 리뷰: "리뷰 작성" 버튼은 항상 보이되, `myReview`가 없고 `hasPlayed`도 false면(=테스트 시작 전이라 플레이 자체가 불가능한 상태 포함) 비활성화 + 호버 시 안내 툴팁
- 개발사 Q&A: 질문 입력창+"질문하기" 버튼은 항상 보이되, 테스트 시작 전이면 둘 다 비활성화 + 입력창 위에 안내 문구 상시 노출
- 라이브존은 이 시점 제한 대상이 아님(플레이 여부만 확인)

`PlayerGameDetailPage.tsx`의 `isTestStarted`(상단에서 공용으로 계산) 값을 리뷰/Q&A 양쪽에서 공유해서 쓴다.

#### 기업 분류 체계

기업 회원은 **두 단계**로 분류됩니다.

```
기업 회원 (memberType=corporate)
├── 개발사 (companyCategory=developer)   ← 게임 개발 주체, 개발자 센터 접근 가능
└── 파트너 (companyCategory=partner)    ← 게임 서비스 관련사, 파트너 라운지 전용
    └── 기업 형태 (companyType, 복수 선택)
        퍼블리셔 / 게임솔루션 / 게임서비스 / 운영 / QA / 마케팅 / 개발 / 원화 / 기타
```

- `companyCategory` = **상위 개념** (개발사 vs 파트너 구분)
- `companyType` = **하위 개념** (기업 형태, 복수 선택 가능)
- 가입 시 `companyCategory`와 `companyType` 모두 **필수**
- 개발사는 게임 등록/관리 가능 (개발자 센터), 파트너는 파트너 라운지 전용

> **하위 호환**: `companyCategory` 필드가 없는 기존 계정은 `companyType.includes('developer')`로 개발사 여부를 판단합니다.

#### 가입 및 승인

```
기업회원 가입 (회사명, 기업 구분(개발사/파트너), 기업 형태, 연락처, 사업자 등록번호 입력)
  ↓
approvalStatus=pending (가입 대기) → /register/pending 화면으로 이동
  ↓
관리자(super) 검토
  ↓
[승인] approvalStatus=approved → 파트너 라운지 채널 자동 생성
[삭제] 계정 완전 삭제 (DB에서 제거)
```

- 기업 승인은 **super 관리자만** 가능
- **거절(rejected) 기능 없음**: 관리자는 승인 또는 계정 삭제만 가능
- 승인된 회원(`approvalStatus=approved`)은 관리자가 삭제 불가 (버튼 비활성화)

#### 사업자 등록번호 입력 (2026-08-07 도입)

- 기업회원 **가입** 및 **재신청(`reapply`)** 시 사업자 등록번호(`123-45-67890` 형식, 숫자 10자리) 입력은 **필수**이며, `companyInfo.businessNumber`에 저장된다
- 파일 첨부가 아닌 **텍스트 입력**이며, 입력 시 자동으로 `-` 구분자가 붙는다
- 관리자 **회원관리 > 기업회원** 목록(`/admin/users-enhanced/corporate`, `AdminCorporateMembersPage`)의 "사업자등록번호" 컬럼에서 확인 가능
- **⚠️ 2026-09-04**: 가입 승인 대기 목록(`/admin/members/new_account`, `AdminMembersPage`)은 컬럼을 No./회사명/담당자(구 "사용자명")/이메일/기업 유형/대표 연락처/가입일/기업 정보/상태/가입 승인 순으로 재정렬하면서 "사업자등록번호"·"사업자 형태" 컬럼을 제거했다(사업자번호 확인은 가입 심사 상세 화면 등 다른 곳에서 하고, 이 목록은 간략하게 유지). `AdminCorporateMembersPage`의 사업자등록번호 컬럼은 그대로 유지됨 — 이 둘은 서로 다른 화면이라 이번 변경이 그쪽엔 영향 없음.

#### 미승인 기업회원 접근 제한

- `approvalStatus=pending` 상태의 기업회원은 `/register/pending`, `/login`, `/terms` 외 모든 페이지 접근 불가
- 접근 시도 시 `/register/pending`으로 자동 리다이렉트
- `/register/pending` 페이지에서 "홈으로 돌아가기" 클릭 시 **로그아웃** 후 홈으로 이동

#### 기업 형태(companyType) 수정

- 승인된 기업회원 대표 계정은 **파트너 라운지 프로필 > 소개 수정** 화면에서 `기업 형태`를 언제든 재설정할 수 있다 (`PATCH /api/users/company-type`)
- 재신청(`reapply`)과 달리 `approvalStatus`를 변경하지 않으며, `companyInfo.companyType`만 갱신된다
- 팀원 계정은 수정 불가 (대표 계정 본인만 가능)
- **가입/재신청과 달리 이 수정 화면에서는 최소 선택 개수 제한이 없다** (전체 해제하여 빈 배열로 저장 가능)

#### 기업 유형(companyCategory) 관리자 수정

- 가입 시 선택한 `companyCategory`(개발사/파트너)가 잘못 분류된 경우, **어드민(normal 이상) > 회원관리 > 기업회원** 목록의 "기업 유형" 컬럼에서 "변경" 버튼으로 되돌릴 수 있다 (`PATCH /api/admin/users-enhanced/:id`)
- 이 API는 전달된 `companyInfo` 필드만 병합 적용하므로, 회사명·사업자번호·기업 형태 등 다른 기업 정보는 유지된다
- 개발사 ↔ 파트너 전환은 접근 가능한 기능이 바뀌는 중요한 변경이므로 `ConfirmModal` 확인 팝업을 거친다

#### 회사 단일 계정 원칙

- **하나의 회사에 하나의 대표 기업회원 계정만** 허용
- 가입 시 동일 회사명(대기/승인 상태)이 이미 존재하면 가입 불가
- 이 계정만 파트너 라운지 채널을 소유함

#### 역할 제한

- 기업회원 계정(`memberType=corporate`)은 **관리자(`role=admin`)로 변경 불가**
- 관리자가 역할 변경 시도 시 403 오류 반환

#### 가입 보안 강화 (2026-09-04, 진행 중)

보안 점검 후 가입 절차를 단계적으로 강화하고 있다. 순서: ① 비밀번호 정책 → ② 회사 웹사이트 등록 → ③ 캡차 → ④ 사업자등록번호 실제 검증.

- **① 비밀번호 정책 강화 (완료)**: 기존 "최소 6자"에서 **"8자 이상 + 영문/숫자/특수문자 모두 포함"**으로 강화. `RegisterPage.tsx`(가입)와 `userController.ts`의 `register`/`changePassword` 양쪽 다 동일 정책(`isValidPassword`) 적용. 가입 화면에는 입력 중 실시간으로 4개 조건 충족 여부를 체크(✓)/엑스(✗)로 보여주는 UI 추가.
- **② 회사 웹사이트 등록 (완료)**: 기업회원 가입 폼에 "회사 웹사이트"(선택 입력) 필드 추가, `companyInfo.homepageUrl`에 저장(기존 파트너 라운지에서만 쓰이던 필드를 가입 흐름에도 연결). 입력 시 URL 형식 서버 검증(`new URL()`).
- **③ 캡차 (완료)**: Cloudflare Turnstile 실제 연동 완료. 가입 폼(Step 3, 비밀번호 카드 바로 아래·기업정보 카드 위)에 위젯 렌더링, 서버(`turnstileService.ts`)가 `siteverify`로 토큰을 재검증한 뒤에만 가입 처리. 위젯은 `render=explicit` + `turnstile.render()` 명시 호출 방식 사용(암묵적 `data-sitekey` 스캔은 위젯이 나중에 마운트되는 다단계 폼에서 렌더링 안 되는 버그가 있어 피함).
- **④ 사업자등록번호 실제 검증 (완료)**: 국세청 "사업자등록번호 상태조회" API(공공데이터포털)로 **번호가 실존하고 휴폐업 상태가 아닌지**만 확인한다(`businessNumberService.ts`). 사업자등록번호 10자리 입력 완료 시 0.5초 디바운스 후 실시간으로 서버(`POST /api/users/verify-business-number`)에 확인 요청 → 카드 아래 확인중/완료/불가 상태 박스로 결과 표시(입력 필드 자체엔 테두리색·문구 안 씀). `register` 시에도 서버가 동일하게 재검증(프론트 우회 방지).
  - **⚠️ 2026-09-04: "진위확인"(번호+대표자명+개업일자 일치까지 확인) 시도했다가 되돌림.** 처음엔 대표자 사칭까지 막으려고 대표자 성명·개업일자 입력란을 추가하고 진위확인 API를 썼는데, 실제 등록된 법인으로 테스트해보니 이름/날짜를 정확히 넣어도 계속 "확인할 수 없음"이 반환됨 — 같은 번호를 상태조회로 단독 조회하면 정상적으로 "계속사업자(활성)"로 인식돼서, 국세청 진위확인 API가 법인 등에서 대표자명 매칭이 불안정한 것으로 판단. 처음엔 "진위확인 실패 시 상태조회로 완화"하는 절충안을 시도했으나, 결국 **대표자 성명·개업일자 입력란과 진위확인 로직 자체를 전부 제거**하고 상태조회 하나로 단순화했다(`User.companyInfo`에도 관련 필드 없음). 대표자 사칭 방지는 현재 검증 범위 밖 — 필요해지면 다른 방법으로 다시 검토.
  - **⚠️ 2026-09-04 레이트리밋 버그(발견 및 수정)**: `POST /users/verify-business-number`에 로그인/가입 전용 `authLimiter`(15분당 10회)를 잘못 걸어둬서, 입력 중 자동 호출되는 이 API가 정상 사용 중에도 금방 429로 막히는 버그가 있었다 — 화면엔 그냥 "확인 중 오류가 발생했습니다"로만 보여서 원인 파악이 어려웠음. `authLimiter` 제거.
  - **전용 레이트리밋 신설 (`businessCheckLimiter`, `rateLimiters.ts`)**: 10분당 20회, 초과 시 메시지 `"잠시 후 다시 시도해주세요."`를 그대로 화면에 표시(요약 박스에 빨간 아이콘 + 해당 메시지). `globalLimiter`와 마찬가지로 **개발 환경에서는 스킵**되어 로컬 테스트에는 영향 없음. 목적: 정상적인 입력/수정 흐름은 막지 않으면서, 외부(국세청) API 사용량 소진이나 번호 무작위 대입 시도만 차단.
  - **`BUSINESS_NUMBER_API_KEY` 미설정 시 검증을 건너뛰고 통과시키는 방식**이라, 키 발급 전인 지금은 사실상 형식 검증만 되는 상태 — 키 발급되면 자동으로 실제 검증이 시작된다.

**별도 발견된 미해결 이슈**: 기업회원은 가입 직후 `approvalStatus=pending`이어도 이미 `role=developer` JWT가 발급돼, 게임 생성 등 개발사 API를 승인 전에도 그대로 호출할 수 있다(프론트 화면 리다이렉트만 있고 API 자체엔 승인 상태 체크가 없음). 위 4단계와는 별개 작업이며 아직 미수정 — 다음에 다룰 때 먼저 확인할 것.

### 2.4 파트너 채널 팀원

- 기업회원 대표 계정은 **내채널 > 팀원 관리**에서 게임회원을 팀원으로 추가할 수 있다
- 팀원으로 추가된 게임회원은 **파트너 라운지 접근 가능** + **채널 수정 권한** (게시글 작성, 채널 프로필 업데이트)
- 팀원 추가/제거는 **채널 소유자(기업 대표 계정)만** 가능 (게임회원 팀원은 팀원 관리 불가)
- 기업회원 계정은 팀원으로 추가 불가
- 채널 소유자 본인도 팀원으로 추가 불가
- `GET /partner/status` 호출 시 팀원 여부(`isTeamMember: true`)와 소속 파트너 정보가 함께 반환됨

### 2.5 계정 정지 (ban)

- 정지 처리: `isActive=false`, `bannedAt` 기록
- 정지 범위(`banScope`): `posts`(게시글), `comments`(댓글), 또는 둘 다
- 정지 기한(`bannedUntil`): 날짜 지정 또는 영구
- **만료일 지나면 자동 해제** (커뮤니티 접근 시 자동 체크)
- 정지/해제 시 `history` 배열에 이력 기록
- 정지/해제 시 해당 사용자에게 **시스템 알림** 자동 발송
- **즉시 차단**: 정지된 계정은 로그인 중이어도 다음 API 요청 시 즉시 차단 (`isActive=false` DB 실시간 확인, `401 ACCOUNT_SUSPENDED` 반환 후 로그아웃)

**정지 불가 계정:**
- `role=admin`인 계정은 정지 체크 제외 (관리자는 항상 접근 가능)

### 2.7 마이페이지 (`/my`) (2026-08-07 개편)

- **개발사/파트너 기업회원은 완전히 동일한 컴포넌트**(`CorporateMyPage.tsx`)를 사용한다. `MyPageRouter`는 기업회원(`memberType=corporate`)이면 개발사/파트너 구분 없이 이 컴포넌트로 라우팅하며, 역할 배지("개발사"/"파트너사")만 `companyInfo.companyCategory`로 자동 판별해 다르게 표시한다
- 탭 구분 없이 한 화면에 **회사 정보(읽기 전용) → 사용자명 → 비밀번호 변경 → 계정 삭제** 순서로 표시된다
  - 회사 정보에는 실제로 가입 시 입력받는 값만 노출한다: 회사명, 사업자등록번호, 대표 연락처, 담당자 이메일. 그 외 임직원 수/회사 전화번호/홈페이지/회사소개 등은 가입 절차에서 입력받지 않는 필드라 표시하지 않는다
  - 회사 정보는 수정 불가(관리자만 변경 가능)이며 별도 안내 문구 없이 값만 표시한다
- 관리자(`AdminMyPage`)·유저(`PlayerMyPage`) 마이페이지도 프로필 헤더 카드를 같은 디자인 톤(어두운 그라디언트 + 블러 블롭 + 프로스티드 글라스 배지, 역할별 색상만 다름: 개발사/파트너=보라, 관리자=빨강/주황, 유저=시안/블루)으로 통일했다

#### 프로필 아바타 업로드

- 기업회원 마이페이지의 "사용자명" 카드 왼쪽에서 프로필 사진을 업로드할 수 있다 (`POST /api/users/avatar`, JPG/PNG/GIF/WEBP, 최대 2MB, `User.profileImage`에 저장)
- 업로드 시 기존 이미지 파일은 서버에서 삭제 후 교체된다
- 프로필 사진이 설정된 계정은 **본인이 보는 화면 전체**(`Navbar`, `AdminLayout`, `DeveloperLayout` 사이드바/헤더, 개발사·파트너·관리자·유저 마이페이지 헤더)에서 글자 아바타 대신 실제 사진이 표시된다
- 소셜 로그인(카카오/네이버) 계정은 가입 시 제공자의 프로필 사진이 `profileImage`로 자동 설정된다
- 게시글 작성자·댓글·쪽지 상대방 등 **다른 사용자에게 보이는** 아바타는 아직 이 기능이 적용되지 않았다 (별도 백엔드 작업 필요)
- 세션에 반영된 최신 프로필 정보를 재조회하려면 `useAuth().updateUser()`가 내부적으로 NextAuth `update({})`를 호출한다 — 인자 없이 `update()`만 호출하면 `auth.ts`의 `trigger==='update'` 분기(백엔드 프로필 재조회)가 실행되지 않아 변경 사항이 세션에 반영되지 않으니 주의

#### ⚠️ `User` 문서 `.save()` 시 레거시 데이터로 인한 500 에러 주의

- production DB의 일부 기업회원 계정은 `companyInfo.companyType` 배열에 스키마 enum에 없는 레거시 값(예: `"개발사"`, 정상 값은 `publisher`/`game_solution`/`game_service`/`operations`/`qa`/`marketing`/`development`/`original_art`/`other`)이 남아있다
- `User.findById()`로 문서 전체를 읽어 필드 하나만 바꾸고 `.save()`하면, Mongoose가 문서 전체를 재검증하면서 이 레거시 enum 값 때문에 **ValidationError → 500 "서버 오류가 발생했습니다"**가 발생한다 (해당 계정만 영향, 정상 데이터를 가진 계정은 문제없음)
- 아바타 업로드(`uploadAvatar`)와 비밀번호 변경(`changePassword`)에서 실제로 이 문제가 발견되어 `findByIdAndUpdate`(부분 업데이트, 전체 재검증 안 함) 방식으로 수정했다 (2026-08-07)
- **`User` 문서를 수정하는 새 코드를 작성할 때는 `findById` + `.save()` 대신 `findByIdAndUpdate`를 사용해야 한다.** `adminController.ts`, `adminUserController.ts`, `gameShopController.ts`, `oauthController.ts` 등에 아직 `findById`+`.save()` 패턴이 남아있어 같은 계정(레거시 `companyType`을 가진 기업회원)에 대해 밴 처리, 포인트 지급/차감, OAuth 연동 등을 시도하면 동일한 500 에러가 날 수 있다 — 아직 수정되지 않았으니 관련 기능에서 오류 제보가 오면 우선 이 원인부터 의심할 것

### 2.8 로그인 보안 — 계정 잠금 (2026-09-08 신설)

- 기존에는 `authLimiter`(IP 기준 15분당 10회)만 있었고, **계정 단위 잠금은 없었다** — 같은 IP에서 15분에 10번까지만 막히므로, IP를 우회하거나 그 이하로 시도하면 특정 계정을 계속 노려도 막을 방법이 없는 상태였음. 이를 보완하기 위해 계정 단위 잠금을 추가로 도입.
- **정책**: 한 계정에 대해 **비밀번호 틀린 로그인 시도가 5회 연속 누적되면, 해당 계정을 15분간 잠근다.** 잠긴 동안에는 올바른 비밀번호를 입력해도 로그인이 거부된다 (`userController.ts`의 `login`, `MAX_LOGIN_ATTEMPTS=5` / `LOGIN_LOCK_DURATION_MS=15분`).
- `User` 모델에 `failedLoginAttempts`(실패 누적 횟수), `lockUntil`(잠금 해제 시각) 필드 추가. 로그인 성공 시 두 필드 모두 초기화된다.
- 잠금 중 로그인 시도 시 응답 메시지에 **남은 시간(분)을 계산해 그대로 보여준다** (예: "로그인 시도 횟수를 초과하여 계정이 잠겼습니다. 12분 후 다시 시도해주세요."). 5회째 실패로 막 잠긴 순간에는 "계정이 15분간 잠겼습니다."로 문구가 약간 다름.
- 재오픈(잠금 조기 해제) 기능은 **관리자 비밀번호 초기화**(`/admin/users-enhanced/[id]`의 "비밀번호 초기화" 버튼 → `resetUserPassword`)에 자동으로 딸려 있다 — 임시 비밀번호 발급 시 `failedLoginAttempts`/`lockUntil`도 함께 초기화되므로, 회원님이 잠겨서 문의하면 관리자는 비밀번호 초기화만 해주면 된다(별도 "잠금 해제" 버튼 없음).
- 프론트: `useAuth.ts`의 `login()`이 NextAuth `signIn()` 전에 `/api/users/login`을 직접 한 번 호출해 실패 시 응답 body의 실제 `message`로 `throw` 한다 — 기존에는 NextAuth credentials `authorize()`가 `res.ok`가 아니면 body를 읽지 않고 그냥 `null`을 반환해서 서버가 내려주는 구체적 메시지(잠금 안내, 계정 정지 안내 등)가 전부 로그인 화면에서 사라지고 항상 "이메일 또는 비밀번호가 올바르지 않습니다"로만 보였음 — 이 부수 효과로 계정 정지(`isActive=false`) 메시지도 이제 같이 제대로 보임.
- 로그인 성공 경로에서는 API가 두 번 호출됨(직접 fetch 1회 + NextAuth `authorize()` 내부 fetch 1회) — 실패 경로는 1회만 호출되므로 브루트포스 시도 횟수 집계에는 영향 없음.

### 2.9 이메일 발송 & 비밀번호 찾기 (2026-09-08 신설)

- **메일 발송 서비스**: Resend(`resend` 패키지)로 연동. `apps/api/src/services/emailService.ts`의 `sendTempPasswordEmail(to, username, tempPassword)` 하나로 공용화되어 있음. Resend 클라이언트는 지연 생성(lazy init)한다 — 모듈 최상단에서 바로 `new Resend(...)`를 하면 `dotenv.config()`(index.ts)보다 먼저 평가돼서 `RESEND_API_KEY`가 빈 값으로 읽히는 버그가 있었음(ESM은 import 트리를 전부 평가한 뒤에 index.ts 본문이 실행되기 때문).
- **발신 도메인**: `gameup.co.kr` 루트 도메인을 Resend에 직접 인증(SPF/DKIM, DNS는 NCP Global DNS에서 관리). 가입 당시 이 도메인에 기존 MX/TXT 레코드가 전혀 없어서 충돌 없이 루트 도메인으로 바로 인증함 — 서브도메인으로 우회할 필요 없었음. `EMAIL_FROM`(`.env`)에 실제 발신 주소 저장, 기본값 `no-reply@gameup.co.kr`.
- **`generateTempPassword()`**: `authService.ts`에 공용 함수로 위치. `Gameup!` + 랜덤 4자리 숫자 형식.
- **로그인 화면 셀프 비밀번호 찾기** (`POST /api/users/forgot-password`, `forgotPassword`): 로그인 화면 "비밀번호를 잊으셨나요?" 버튼 → 이메일 입력 모달 → 본인이 직접 임시 비밀번호를 이메일로 받음. `authLimiter`(15분당 10회, `/login`과 동일 버킷 공유) 적용.
  - **계정 존재 여부를 노출하지 않는다**: 입력한 이메일이 실제 가입 계정이든 아니든, 메일 발송에 성공하든 실패하든 **항상 동일한 문구**("입력하신 이메일로 가입된 계정이 있다면, 임시 비밀번호를 보내드렸습니다.")만 반환한다. 이렇게 안 하면 응답 차이로 "이 이메일이 가입되어 있는지"를 외부에서 알아낼 수 있음(계정 존재 여부 스캐닝 방지).
  - 메일 발송 성공 시에만 DB 비밀번호를 갱신하고, 성공 시 `failedLoginAttempts`/`lockUntil`(2.8 계정 잠금)도 함께 초기화된다.
- **⚠️ 관리자 비밀번호 초기화 기능은 제거됨(2026-09-08)**: 원래 `/admin/users-enhanced/[id]`에 "비밀번호 초기화" 버튼(`resetUserPassword`)이 있었으나, 위 셀프 비밀번호 찾기 기능이 생기면서 회원님이 직접 처리 가능해져 **중복 기능으로 판단, 완전히 제거**했다(버튼/모달/컨트롤러/라우트/서비스 함수 전부 삭제). 계정이 잠겼거나(2.8) 비밀번호를 잊은 회원은 이제 로그인 화면에서 셀프로 해결하며, 관리자가 대신 눌러줄 방법은 없다.
- **이메일(아이디) 찾기 기능은 없음 — 보류 결정(2026-09-08)**: 로그인 ID가 이메일 자체인데, 일반 게임회원(플레이어)은 가입 시 전화번호 등 대체 식별자를 아예 안 받기 때문에 "이메일을 잊었을 때 찾을 방법"이 지금 구조로는 없다. 검토했던 대안: ① 가입 폼에 전화번호 필수화 후 전화번호로 조회하는 기능 신설(범위 큼) ② 문의하기 탭(11장)으로 관리자에게 직접 문의해서 확인받기(코드 변경 없이 바로 가능). 사용자가 "일단 없이간다"고 결정 — 새로 만들지 않고, 필요해지면 위 두 대안 중 골라서 재검토.

### 2.10 2단계 인증 (OTP/TOTP) — 본인 선택제 (2026-09-09 신설)

- **가입 시 강제 아님 — 가입 후 마이페이지에서 본인이 켜고 끄는 선택 기능**이다. Google Authenticator 등 TOTP(RFC 6238) 인증 앱을 쓰며, 이메일/SMS 발송이 필요 없어 2.9의 발송 한도·비용과 무관하다.
- 플레이어/기업/관리자 마이페이지(`/my`) **보안 설정 탭 3곳 전부에 동일하게** 공용 컴포넌트 `apps/web/src/components/TwoFactorSettings.tsx`로 노출된다 — 하나를 수정하면 셋 다 자동 반영.
- **켜는 절차**: `POST /users/2fa/setup`으로 시크릿+QR 발급(아직 비활성) → 인증 앱에 등록 후 6자리 코드로 `POST /users/2fa/enable` 확인 → 성공 시 그제서야 `User.twoFactorEnabled=true`, 동시에 **1회용 백업 코드 10개**(`twoFactorBackupCodes`, bcrypt 해시 저장)를 발급해 그 응답에서만 평문으로 보여준다(다시 볼 수 없음, 인증 앱 분실 대비).
- **끄는 절차**: `POST /users/2fa/disable`, 계정 삭제·비밀번호 초기화 재사용 초기화와 동일하게 **현재 비밀번호 확인**으로 본인 인증한다(TOTP 코드 재확인 아님 — 인증 앱을 분실한 상태에서도 해제할 수 있어야 하므로).
- **로그인 분기**: 로그인 API(`POST /users/login`) 하나에 선택 필드 `totpCode`를 추가하는 방식으로 처리한다(별도 임시토큰/2차 엔드포인트 없음). `user.twoFactorEnabled`인 계정이 코드 없이 로그인하면 토큰 미발급 상태로 `{requires2FA:true}`만 응답 → 로그인 화면이 6자리 코드 입력 단계로 전환 → 코드와 함께 같은 이메일/비밀번호로 재요청하면 검증 후 정상 토큰 발급. NextAuth `authorize()`도 `totpCode` 필드만 추가로 실어 나른다.
- **백업 코드도 로그인 시 `totpCode` 자리에 그대로 입력 가능** (TOTP 실패 시 백업 코드 목록에서 매칭 시도) — 매칭되면 그 코드는 즉시 소모(재사용 불가).
- 2FA 코드 오답은 2.8의 계정 잠금 카운터(`failedLoginAttempts`)에 포함되지 않는다 — 비밀번호 오답만 잠금에 집계된다.

### 3.4 회원 상세정보 페이지 (`/admin/users-enhanced/[id]`, `AdminUserDetailPage`, 2026-09-04~07 개편)

관리자 회원관리 목록 각 화면("보기")에서 진입하는 공용 상세정보 화면. 실제 스키마(`companyInfo`/`contactPerson` 등)에 맞춰 재구성했으며, **회원 유형(기업회원/게임회원/관리자)마다 레이아웃을 다르게 구성**한다 — 상단에 유형을 나타내는 배지(뱃지)는 넣지 않고, 대신 화면 제목과 섹션 구성 자체로 유형을 구분한다.

| 회원 유형 판별 기준 | 화면 제목 | 표시 섹션 |
|---|---|---|
| `role === 'admin'` | 관리자 계정 상세정보 | 계정 정보(관리자 권한 정보 없음, 활동점수/캡코인 제외), 관리자 권한 정보(권한 등급/부여일, 읽기전용), 관리자 메모 |

### 5.8 게임 공지사항 (GameAnnouncement) — 커뮤니티 게시글(Post)과 별개 기능 (2026-08-11 정리)

**커뮤니티 게시글(`Post`)과 게임 공지사항(`GameAnnouncement`)은 완전히 다른 컬렉션/기능이다.** 화면에 같이 보일 때가 있어서 헷갈리기 쉬우니 아래 표로 구분한다.

| | 커뮤니티 게시글 (Post) | 게임 공지사항 (GameAnnouncement) |
|---|---|---|
| 작성 위치 | 커뮤니티 "글쓰기" (유저/개발사 누구나) | 개발사 콘솔 `게임 관리 > 공지 & 알림` 탭 (게임 소유 개발사 또는 admin만) |
| 데이터 | `channel`(자유/라이브게임 등)로 분류 | `gameId`로 특정 게임 1개에 귀속, `type`(notice/update/maintenance/event) |
| 노출 위치 | 커뮤니티 채널 탭(`/community?channel=...`) 목록 | ① 커뮤니티 홈의 "게임별 공지사항" 위젯 ② 특정 게임의 커뮤니티 페이지(`?gameId=...`) 상단 "OO 공지사항" 박스 ③ 자체 상세페이지 `/community/game-announcement/[id]` |

**핵심: 게임 공지사항은 채널 탭의 게시글 목록에는 절대 섞이지 않는다.** `channel=live-game`처럼 `gameId` 없이 채널만 필터한 목록은 `Post`만 조회하고, 특정 게임(`gameId` 포함) 페이지에서만 공지사항 박스가 게시글 목록 위에 별도로 붙는다.

**뷰 모드(대형/중형/소형) 토글은 게시글 목록에만 적용된다.** 게임 공지사항 박스(`CommunityPage.tsx`의 "OO 공지사항" `<ul><li>` 영역)는 게시글용 `viewMode` state를 참조하지 않고 항상 같은 리스트 스타일로 고정 렌더링된다. "소형으로 고정하기로 결정"한 게 아니라, 애초에 공지사항 박스에는 대형/중형 뷰가 구현된 적이 없다 — 대형 뷰 자체는 게시글 카드에만 존재한다.

**푸시 알림 발송 기능은 없다 (2026-08-11 UI 제거).** 예전에 공지 작성 모달에 "푸시 알림 전송" 체크박스가 있었지만, 체크해도 실제로 FCM/웹푸시/이메일 등 어떤 발송도 하지 않고 DB에 플래그만 기록하는 허위 기능이어서 체크박스 자체를 제거했다. `GameAnnouncement` 스키마의 `sendPush`/`recipients` 필드는 과거 데이터 호환을 위해 남아있지만 신규 생성 시 더 이상 채워지지 않는다.

### 5.9 삭제 처리 (소프트 삭제 → 삭제 보관함 → 복구/완전삭제)

**게시글(Post), 플랫폼 공지(Announcement), 게임 공지(GameAnnouncement) 전부 동일한 소프트 삭제 방식을 쓴다 (2026-08-13, Announcement/GameAnnouncement에도 확장 적용).**

- 관리자(또는 개발자, 게임 공지의 경우)가 "삭제"를 누르면 실제로 DB에서 지워지지 않고 삭제 마커만 찍힌다 — Post는 `status: 'deleted'` + `deletedAt`, Announcement/GameAnnouncement는 `deletedAt`. 목록/공개 화면에서는 삭제 마커가 찍힌 항목을 필터링해서 안 보이게 할 뿐이다.
- 삭제된 항목은 관리자 화면 `/admin/community/reported/deleted` ("삭제 게시물 관리")에 전부 모여서 보인다 — 게시글/플랫폼공지/게임공지를 하나의 표로 합쳐서 보여준다(카테고리 컬럼으로 구분: 채널명 또는 게임명 또는 "공지").
- 여기서 **복구**(삭제 이전 상태로 되돌림, 실제로 다시 노출됨)하거나 **완전 삭제**(진짜로 DB에서 제거, 되돌릴 수 없음)를 선택할 수 있다.
- **완전 삭제는 소프트 삭제된 것만 가능** — 아직 삭제 안 한 항목을 완전 삭제 API로 바로 지울 수 없다(먼저 소프트 삭제 → 그 다음 완전 삭제 2단계).
- 공지사항(Announcement/GameAnnouncement) 삭제/복구/완전삭제는 관리자 등급 중 `super`만 가능 (게임 공지 삭제 자체는 게임 소유 개발자도 가능하지만, 삭제된 걸 관리자 화면에서 복구/완전삭제하는 건 super 전용).
- ⚠️ **2026-08-13 이전에 삭제된 공지(Announcement)는 하드 삭제였기 때문에 복구 불가** — 이 날짜 이후 삭제분부터 소프트 삭제 방식이 적용되어 삭제 보관함에 뜨고 복구 가능하다.

### 5.10 즐겨찾기 — "게시글 즐겨찾기"가 아니라 "탭 즐겨찾기" (2026-08-14 개편)

**2026-08-14 이전에는 게시글/플랫폼공지/게임공지 각각에 개별 즐겨찾기(북마크) 버튼이 있었다. 지금은 전부 제거됐고, 대신 커뮤니티 사이드바의 "탭"(채널·게임 목록)을 즐겨찾기하는 기능으로 완전히 대체됐다.**

- 콘텐츠 하나하나(게시글/공지)를 즐겨찾기하는 기능은 더 이상 없다 — `Post`/`Announcement`/`GameAnnouncement` 세 모델 모두 `bookmarks` 필드와 토글 API가 완전히 삭제됨.
- 대신 커뮤니티 사이드바(데스크톱)에서 각 탭(신작게임소개/베타게임/라이브게임/자유게시판/공지사항의 게임업공지·게임공지 하위 탭)과, 베타게임/라이브게임 하위의 개별 게임 항목 옆에 별표(★) 아이콘이 있다. 누르면 `User.bookmarkedTabs` 배열에 `{key, label, channel, gameId?}` 형태로 추가/제거된다.
- 별표를 눌러도 **그 탭이 사이드바에서 이동하거나 복제되지 않는다** — 원래 위치 그대로 있고, 대신 "즐겨찾기" 탭에 들어가면 즐겨찾기한 탭들의 바로가기 목록이 보인다 (클릭하면 해당 탭/게임으로 바로 이동).
- 홈/즐겨찾기 탭 자체는 즐겨찾기 대상이 아니다. 모바일 사이드바(하단 가로 스크롤 탭)에는 별표가 없다 — 모바일은 애초에 게임 하위 목록도 안 보여주는 단순화된 네비게이션이라 탭 즐겨찾기 기능 자체가 없음.
- 관련 엔드포인트: `POST /api/users/bookmarked-tabs/toggle`, `GET /api/users/profile` 응답에 `bookmarkedTabs` 포함. NextAuth 세션에도 반영되어 `useAuth()`의 `user.bookmarkedTabs`로 프론트 어디서든 접근 가능.

### 5.11 공개/비공개 (isPublished) — 2026-08-20 신설

**게시글(Post), 플랫폼 공지(Announcement), 게임 공지(GameAnnouncement) 전부 작성 시점에 공개/비공개를 선택할 수 있다.** 기본값은 항상 공개(`isPublished: true`)이며, 작성/수정 화면에 초록색 토글(공개) ↔ 회색 토글(비공개)로 표시된다.

- **작성 화면 위치**:
  - 커뮤니티 게시글: `CommunityWritePage.tsx` 헤더 우측 (제목 "게시글 작성"/"게시글 수정" 옆)
  - 플랫폼 공지/게임 공지: 공용 컴포넌트 `AnnouncementManager.tsx`의 작성/수정 모달 하단, "공개 여부" 라벨과 함께 — 관리자 공지(`AdminCommunityPage.tsx`)와 개발자 게임 공지(`GameDetailManagementPage.tsx`) 양쪽에 동일하게 노출된다 (이 컴포넌트를 쓰는 특성상 자동 반영).
- **비공개 게시물의 노출 범위**: 목록(피드/사이드바 위젯/핫게시글/통계 등)과 상세페이지 둘 다에서, **작성자 본인과 관리자에게만** 보인다. 그 외(비로그인 포함 모든 타 사용자)에게는 존재 자체가 안 보임 — 목록에서 빠지고, 상세 URL로 직접 접근해도 404(찾을 수 없음) 처리된다.
- 게임 공지의 경우 "소유자"는 그 게임의 개발사(`developerId`) 또는 admin이다. 다른 개발사 계정은 타 사용자와 동일하게 비공개 게임 공지를 볼 수 없다.
- 소프트 삭제(5.9)와는 무관한 별개 상태다 — 비공개도 소프트 삭제된 것도 아니고, "작성자만 볼 수 있는 비공개 게시물"이라는 정상 상태다. 관리자 화면의 "삭제 게시물 관리"에도 나타나지 않는다.
- 언제든 작성자(또는 관리자)가 수정 화면에서 토글을 다시 바꿔 공개↔비공개를 전환할 수 있다.

### 5.12 댓글 정렬 & 베스트 댓글 (2026-08-26 신설)

**댓글은 좋아요/싫어요(추천/비추천)를 모두 가질 수 있고(상호 배타적 — 하나 누르면 반대쪽 자동 해제), 이를 이용한 "베스트순" 정렬과 "베스트" 배지가 있다.** 관련 코드는 `apps/web/src/components/community/CommentSection.tsx`(공용 컴포넌트) + `apps/web/src/lib/wilsonScore.ts`.

- **정렬 옵션**: "최신순"(기본값, 등록 순서) / "베스트순" 두 가지를 사용자가 토글로 선택. 답글(대댓글)은 항상 부모 댓글 밑에 등록순으로 그대로 붙어있고, 정렬 대상은 **최상위 댓글(root)에만** 적용된다.
- **베스트순 점수 계산 (Wilson Score 신뢰구간 하한, 95%)**:
  ```
  n = 좋아요 + 싫어요
  score = 0                                    (n = 0일 때)
  phat = 좋아요 / n
  z = 1.96
  score = (phat + z²/2n - z·sqrt((phat(1-phat) + z²/4n) / n)) / (1 + z²/n)   (n > 0일 때)
  ```
  단순 "좋아요 개수순"이 아니라, 표본(투표 수)이 적으면 점수를 보수적으로 깎는 방식 — 좋아요 1개뿐인 댓글이 좋아요 50개(싫어요 5개)인 댓글보다 위로 오는 것을 방지한다. 게시글 "핫 스코어"(5.3)와는 별개의 알고리즘이며 시간 감쇠는 포함하지 않는다.
- **"베스트 댓글" 선정 조건** (아래 둘 다 만족해야 함, 최상위 댓글/답글 구분 없이 동일하게 적용):
  1. 순추천(좋아요 − 싫어요) > 0
  2. 총 투표 수(좋아요 + 싫어요) ≥ **5표** — 표가 거의 없는데 우연히 1등인 경우를 제외하기 위한 최소 기준
  - 조건을 만족하는 댓글 중 Wilson Score 상위 **게시글당 최대 3개**까지 "베스트 댓글"이 된다. 답글(대댓글)도 동일한 자격으로 후보에 포함된다 — 답글이 일반 최상위 댓글보다 점수가 높으면 답글이 베스트가 될 수 있다.
- **베스트 댓글 표시 방식**: 정렬 모드(최신순/베스트순)와 무관하게 **항상** 댓글 입력창 바로 아래에 "🏆 베스트 댓글" 섹션이 나타나고, 선정된 댓글이 원본과 별도로 **다른 색(주황색 강조) 카드**로 복사되어 보인다. 이 복사 카드에는 **답글이 따라오지 않는다**(답글 버튼도 숨김) — 원본 댓글은 스레드 내 원래 위치(답글이면 부모 밑)에도 그대로 남아있고, 그 자리에서도 동일하게 "🏆 베스트" 배지가 붙는다. 베스트 댓글이 하나도 없으면 이 섹션 자체가 렌더링되지 않는다.
- 좋아요/싫어요 아이콘은 엄지(👍/👎), 표시 순서는 **답글 → 좋아요 → 좋아요-싫어요 순점수 → 싫어요 → 신고**. 신고는 다른 액션보다 작고 회색으로 톤 다운. 댓글 작성자 전용 수정/삭제는 액션 줄이 아니라 댓글 상단(닉네임·날짜 옆) 오른쪽 끝에 별도 배치.
- "최신순/베스트순" 토글은 **최상위 댓글의 나열 순서만** 바꾼다 (답글은 항상 부모 밑에 등록순 고정) — 위 "베스트 댓글" 카드 섹션과는 별개 기능이다.
- `CommentSection`이 커뮤니티 게시글 상세(`CommunityPostPage.tsx`)와 관리자 신작게임소개 관리(`AdminCommunityPage.tsx`) 양쪽에서 공유되므로, 이 알고리즘/레이아웃을 고치면 두 화면에 동시에 반영된다.

## 6. 포인트 & 레벨 시스템

### 6.1 활동점수(포인트) 개요

플랫폼 활동에 따라 포인트가 적립되며, 포인트 누적량에 따라 레벨이 자동 계산됩니다.

- `isActive=false` (정지된 계정)
- 만료되지 않은 `bannedUntil` 기한 중
- 해당 타입의 `dailyLimit` 초과 시
- 해당 정책이 `isActive=false`인 경우 (관리자 수동 제외)

## 8. 결제 & 게임샵

### 8.1 결제 수단

- **뉴플레이(NewPlay) Checkout API가 메인 결제수단**, Toss Payments SDK는 구석의 작은 버튼("Toss로 결제")으로 남긴 보조 결제수단 (2026-09-16~)
- 뉴플레이: 결제 생성(`POST /api/payment`) → `paymentUrl`로 리다이렉트 → 유저가 뉴플레이 결제 페이지에서 결제 → 뉴플레이가 웹훅(`POST /api/payments/webhook/newplay`)으로 완료 통지 → 우리 서버가 `Payment.status`를 `completed`로 갱신
  - 웹훅은 `X-Newplay-Signature`(raw body를 `apiSecret`으로 HMAC-SHA256 서명) 검증 후에만 처리, 실패 시 401
  - 뉴플레이가 최대 3회 재시도할 수 있어 이미 `completed`인 주문은 재처리하지 않음(멱등 처리)
  - 유저가 뉴플레이 결제 페이지에서 돌아오면 `/payment/newplay/status?orderId=...`에서 우리 DB 상태를 폴링해서 결과 표시 (뉴플레이 리다이렉트 파라미터 자체는 신뢰하지 않음)
- Toss: 기존과 동일 — 주문 생성 → 결제창(`TossPaymentModal`) → 결제 승인(`/payment/success`) → 완료/실패
- **주문 생성 시 금액/상품명은 클라이언트 입력을 신뢰하지 않고 서버가 재조회해서 확정한다** — `itemId`가 있으면 `GameShopItem`(`saleStatus=on_sale`인 것만), 없으면(게임 자체 유료 구매) `Game.price`를 서버에서 조회해 사용. 클라이언트가 보낸 `amount`/`itemName`은 사용하지 않음 (조작 방지)

### 8.2 게임샵 결제 유형

| 유형 | 값 |
|------|----|
| 현금 결제 (뉴플레이 메인 / Toss 보조) | `cash` |
| 캡코인(플랫폼 포인트) 결제 — **정책 미확정, 재설계 예정** | `capcoin` |

- 캡코인 결제는 PG를 거치지 않는 내부 포인트(`User.points`) 차감이라 뉴플레이/Toss와 무관하며, **뉴플레이/Toss 결제 연동 범위에서 완전히 제외**한다 (2026-09-16 확정)
- 지금 구조(관리자 수동 지급이 사실상 유일한 획득 경로)는 확정된 게 아니고 폐기될 예정 — **향후 "챌린지" 기능이 구현되면, 챌린지 완료 보상으로 얻는 "미션 토큰"으로 재설계되어 그걸로 상점 상품을 구매하는 방식이 될 예정**이다 (챌린지 시스템 자체는 아직 미구현)
- 그 전까지는 캡코인/포인트 결제를 현금 충전 가능하게 만들거나, PG와 연결하는 작업을 하지 않는다

### 8.3 게임샵 상품 심사

- 개발자가 상품 등록 시 `saleStatus=reviewing`
- 관리자(normal+)가 승인 → `saleStatus=on_sale`
- 관리자(normal+)가 거부 → `saleStatus=rejected`

### 8.4 수익화 모델 (monetization)

| 값 | 의미 |
|----|------|
| `free` | 무료 |
| `ad` | 광고형 |
| `paid` | 유료 |
| `freemium` | 부분 유료 (기본값) |

### 8.5 뉴플레이 연동 범위 (2026-09-16 기준)

- 게임샵 결제수단 연동만 진행 — 정기결제(구독), 게임키 판매(Key Checkout), 캡코인(포인트) 결제는 범위 밖 (캡코인은 8.2 참고, 향후 "미션 토큰" 체계로 재설계 예정이라 별도 확정 전까지 손대지 않음)
- 게임사는 뉴플레이와 별도 계약/등록이 필요 없음 — 게임업 플랫폼이 뉴플레이의 단일 파트너이며, 결제 1건마다 `gameId`를 물고 있어 게임이 플랫폼에 등록되는 순간 자동으로 결제가 붙는 구조
- 단, "게임업이 한 가맹점으로 수납한 돈을 게임사별로 나눠 정산 지급"하는 부분은 미구현 — `Settlement` 모델은 스키마만 존재하고 실제 `Payment` 데이터를 집계하는 로직은 없음(목업 시드만 있음)
- 이 작업 시점에 뉴플레이 실 API 인증정보(`apiSecret` 등)가 없어 `apps/api/src/services/newplayService.ts`는 스캐폴딩 상태 — 실 크리덴셜 발급 후 `.env`에 값만 채우면 되나, 뉴플레이 원문 문서 대조 1회(요청 헤더/필드명 확인)가 필요함

### 9.1-1 기업회원 정보 관리 구분

기업회원의 정보는 **기업 정보**와 **개인 정보** 두 곳으로 구분하여 관리합니다.

### 9.5 프로젝트 관리 (관리자, `/admin/partner-topics`)

> 2026-07-06: 상태값을 `모집중 / 매칭성공 / 매칭보류` 3단계로 재구성 (기존 초안/진행중/완료/취소 폐지), "삭제 & 복구" 방식 도입

- 프로젝트 상태값: **`모집중(recruiting)`** / **`매칭성공(matched)`** / **`매칭보류(unmatched)`** 3가지만 존재
  - `모집중`: 지원자를 받을 수 있는 상태. 지원 API(`applyToProject`)는 이 상태에서만 허용됨
  - `매칭성공`: 지원자가 결정되어 모집이 종료되고 프로젝트가 진행되는 상태 (기존 `진행중`을 대체)
  - `매칭보류`: 모집은 종료되었지만 지원자가 아직 결정되지 않은 상태 (기존 `완료`를 대체 — 내부 DB 값은 `unmatched`를 그대로 사용)
  - 기존 `초안(draft)` / `취소(cancelled)`는 폐지됨 — 프로젝트 등록 시 바로 `모집중`으로 생성되며(임시저장 없음), 취소가 필요한 경우는 상태 변경이 아닌 **삭제**로 처리

**지원서 상태값과 최종 결정** (2026-07-24 도입, 2026-07-27 전면 개편 — 승인 2단계 폐지)
- 지원서 상태값: `pending(검토중)` / `approved(협의 중, 레거시)` / `on-hold(보류중)` / `rejected(거절)` / `confirmed(확정)` 5가지
- **승인(approved) 단계는 수동 승인 버튼으로는 폐지됨** — 예전에는 지원자를 먼저 "승인"해야 메시지를 보내고 대화 후 확정할 수 있었지만(2026-07-24 도입), 이 중간 단계를 없애고 **pending 상태에서 바로 메시지 발신 → 확정**이 가능하도록 단순화함(2026-07-27)
- **첫 메시지 발신 시 pending → approved 자동 전환(2026-07-27 추가)** — `sendApplicationMessage`에서 지원서 상태가 아직 `pending`이면 메시지 생성과 함께 자동으로 `approved`("협의 중")로 바뀜. 수동 승인 버튼은 없지만, 대화가 시작됐다는 사실 자체가 "협의 중" 상태를 나타냄. 이미 `on-hold`/`rejected`/`confirmed`인 지원서는 건드리지 않음
- **거절(rejected)과 확정(confirmed)은 둘 다 영구적인 최종 결정** — 한 번 거절되거나 확정되면 어떤 상태로도 다시 바꿀 수 없음(`updateApplicationStatus`가 대상 지원서가 이미 `rejected` 또는 `confirmed`면 무조건 400 응답). 지원자 목록 화면에서도 해당 행의 확정/거절 버튼이 영구 비활성화됨
- **확정(confirmed)**: 지원자 목록에 별도 "확정" 컬럼은 없음 — "협의 하기" 버튼으로 여는 메시지 팝업(`MessageComposeModal`) 안의 "매칭 확정" 버튼으로 처리(§9.7 참고). 그 지원자와 주고받은 메시지가 하나라도 있어야 활성화됨(승인 단계가 없어졌으므로 "대화가 있었는지"가 확정 가능 조건). 클릭 시 `ConfirmModal`로 재확인 후 처리
- **확정(confirmed) 처리 시 자동 처리** (`updateApplicationStatus`, `partnerProjectController.ts`):
  - 같은 프로젝트의 아직 최종 결정(거절/확정) 안 된 다른 지원서 전부 자동으로 `거절(rejected)` 처리
  - 프로젝트 상태 자동으로 `매칭성공`으로 전환 (확정이 영구적이므로 이후 다시 `모집중`/`매칭보류`로 되돌아가지 않음)
- 매시간 배치 작업(`apps/api/src/jobs/closeExpiredProjects.ts`, 서버 시작 시 1회 + 이후 1시간마다)이 `모집중` 상태이면서 `applicationDeadline`이 지난 프로젝트를 검사 → **확정된** 지원자가 있으면 `매칭성공`, 없으면 `매칭보류`로 자동 전환
- `매칭보류` 상태의 프로젝트를 소유자가 `applicationDeadline`을 미래 날짜로 수정하면 → 상태가 `모집중`으로 자동 전환 (`updateProject`, `partnerProjectController.ts`). `매칭성공`은 이미 지원자가 확정된 상태이므로 마감일을 바꿔도 전환되지 않음

**마감 후 거절/확정 제한** (2026-07-07 도입, 2026-07-27 승인 폐지 반영해 갱신)
- `applicationDeadline`이 지난 프로젝트는 아직 확정되지 않은 지원서를 새로 거절할 수 없음 — 지원자 목록 화면(`ProjectsApplicantsView.tsx`)의 거절 버튼이 비활성화되고, API(`updateApplicationStatus`)도 동일 조건으로 400 응답 처리
- **확정(confirmed) 처리 자체는 마감 여부와 무관하게 항상 허용** — 모집은 마감됐어도 이미 대화해둔 후보들 중 최종 1곳을 고르는 절차이기 때문
- **마감된 프로젝트의 미결(pending/approved) 지원 건은 지원자 목록의 "진행 상태" 컬럼(구 "결정")이 상태 배지 대신 "마감"으로 표시되고, "협의 하기" 버튼도 비활성화됨**(프론트 전용 표시 변경 — API 차단은 아님) — 이미 `확정`/`거절`로 최종 결정된 건은 그 결과를 그대로 보여줘야 하므로 이 표시 변경에서 제외됨

**지원 취소 및 재지원** (2026-07-27 추가)
- 지원자 본인은 본인 채널의 **내가 한 지원** 탭에서 "취소" 버튼으로 자신의 지원서를 언제든 취소할 수 있음(단, `confirmed` 상태는 취소 불가) — 취소 시 지원서 자체가 삭제되고(`DELETE /partner/applications/:appId`) 프로젝트 `applicantCount`가 차감됨

- 독립 운영되던 `/minihome-manage` 화면은 폐지되고 파트너 프로필 관리로 완전히 흡수됨

### 9.7 파트너 쪽지(메시지)

> 파트너 채널 간 1:1 쪽지 기능. **2026-07-27 전면 개편**: 승인(approved) 게이트를 없애고, 메시지 발신/수신·히스토리 열람·매칭 확정을 전부 지원자 목록·내가 한 지원의 **"협의 하기"** 버튼 하나(`MessageComposeModal`)로 통합. 별도의 "받은 메시지" 편지함 탭 자체가 폐지됨(9.6절 참고).

**메시지 발신 조건 (2026-07-27 변경)**
- 지원서 상태와 무관하게(`pending`/`rejected` 포함) 프로젝트 소유자와 지원자는 언제든 서로 메시지를 보낼 수 있음 — 과거의 "매칭승인/확정 상태에서만 발신 가능" 제한(2026-07-24 도입)은 폐지됨
- 발신 위치: 소유자는 **채널 관리 > 프로젝트 활동 > 지원자 목록**의 "협의 하기" 컬럼, 지원자는 본인 채널의 **내가 한 지원** 탭의 "협의 하기" 컬럼 — 둘 다 클릭 시 공용 `MessageComposeModal`(작성 + 히스토리 보기 토글)이 뜨며, `ProjectApplication._id` 기준으로 상대를 특정해 발신(`POST /partner/applications/:appId/message`). 히스토리 조회(`GET /partner/applications/:appId/messages`)도 같은 지원 건 기준 — 같은 회사와 다른 프로젝트에서 나눈 무관한 대화가 섞이지 않도록 상대방(counterpart) 기준이 아니라 일부러 지원 건 기준으로 스코프함
- 버튼은 이미 대화가 있었는지 여부와 무관하게 항상 새 메시지 작성 모달을 띄움(예전의 "대화 중" 링크/받은 메시지 탭으로의 자동 이동은 폐지) — 이전 대화 확인은 모달 안의 "히스토리 보기" 토글로 함
- 파트너 찾기(`/partner/directory`) 목록의 "연락하기" 버튼 및 파트너 채널 아무 곳에나 보낼 수 있던 범용 발신 API(`POST /partner/:partnerId/messages`)는 이미 폐지된 상태(2026-07-24)이며 그대로 유지
- 본인에게는 메시지를 보낼 수 없음 (프로젝트 소유자가 자기 프로젝트에 지원하는 경우는 애초에 발생하지 않음)
- **이메일/전화번호 등 연락처 포함 메시지는 차단됨(2026-07-27 추가)** — `containsContactInfo`(`apps/api/src/utils/contactInfoFilter.ts`)가 이메일 형식 또는 전화번호 형식(구분자 있는/없는 9~12자리 숫자열)을 감지하면 400으로 거부. `sendApplicationMessage`와 (더 이상 프론트에서 안 쓰지만 남아있는) `replyToPartnerMessage` 둘 다 적용. 메시지 작성 입력창 placeholder에도 "이메일 주소, 전화 번호 등을 보내지 못할 수 있습니다." 안내 문구 표시
- **지원자는 먼저 대화를 시작할 수 없음(2026-07-27 추가)** — 프로젝트 소유자와 지원자 사이에 주고받은 메시지가 하나도 없으면 지원자 쪽 발신은 403으로 차단됨(`sendApplicationMessage`, 이 지원 건뿐 아니라 두 사람 사이 전체 메시지 기준). 소유자가 먼저 연락한 뒤에만 지원자가 답할 수 있음. 프론트에서는 "내가 한 지원" 탭의 협의 하기 버튼이 대화가 없을 땐 클릭 불가한 "기다리는 중"(시계 아이콘)으로 표시되고, 소유자 쪽은 이 제한이 없어 "협의 시작" 버튼이 항상 활성화됨
- **거절된 지원 건은 지원자 쪽에서 더 이상 협의 불가(2026-07-27 추가)** — `application.status === 'rejected'`면 지원자 쪽 발신은 403으로 차단(`sendApplicationMessage`). "내가 한 지원" 탭에서 협의 하기 버튼이 X 아이콘의 "거절됨"(빨간 톤, 클릭 불가)으로 바뀜. 소유자 쪽은 이 제한이 없어 거절 후에도 계속 메시지를 보낼 수 있음(예: 정중한 안내 메시지)

**협의 하기 버튼의 우편 아이콘 & 안읽음 배지 (2026-07-27 추가)**
- "협의 하기" 버튼은 텍스트 대신 그 상대와의 대화 방향에 따라 3가지 우편 아이콘 중 하나를 보여줌: 대화 없음(`Mail`) / 내가 마지막으로 보내고 아직 답장 없음(`MailCheck`) / 상대가 마지막으로 보냄(`MailOpen`) — `mailButtonState.ts`의 `getMailButtonState`로 계산
- **안읽음 배지(작은 빨간 점)는 이제 이 우편 아이콘 위(오른쪽 상단)에만 표시됨** — 상대가 보낸 최신 메시지를 아직 "본 것"으로 표시하지 않았을 때만 뜸. 예전에 받은 메시지 탭 카드마다 뜨던 "NEW" 배지는 폐지됨(대신 아래 참고)
- 협의 하기 버튼을 클릭해 모달을 열면(또는 그 지원 건을 거절/확정 처리하면) 그 상대의 안읽음 상태가 즉시 "본 것"으로 처리됨(`markMessageSeen`, `ProjectsApplicantsView.tsx`/`ProjectsApplicationsView.tsx`) — `localStorage` 키(`partnerMessageCardSeen:{partnerId}`)에 기록되므로 지원자 목록/내가 한 지원 등 같은 상대를 표시하는 다른 화면에도 즉시 반영됨

**"받은 메시지" 편지함 탭 자체가 폐지됨 (2026-07-27 변경)**
- 전용 편지함 화면(`ReceivedMessagesSection.tsx`)이 삭제되어, 메시지 열람은 오직 "협의 하기" 버튼으로 여는 `MessageComposeModal` 안(작성 / 히스토리 보기 두 화면)에서만 이뤄짐 — 답장 작성, 프로필 보기 등 편지함 화면에 있던 다른 기능은 없음
- **매칭 확정도 이 모달 안에 있음** — 지원자 목록 테이블에 별도 "확정" 컬럼은 없고, 협의 하기 버튼을 눌러 뜨는 모달의 작성 화면 하단 왼쪽에 "매칭 확정" 버튼이 있음. 그 지원자와 주고받은 메시지가 하나라도 있어야 활성화됨(9.5절 참고). **프로젝트를 등록한 소유자(파트너) 쪽에만 노출** — 지원자 본인의 "내가 한 지원" 화면의 협의 하기 팝업에는 이 버튼이 뜨지 않음(`MessageComposeModal`의 `confirmMatch` prop을 소유자 쪽 화면에서만 넘김)

**매칭 확정 시 연락처 상호 공개 (2026-07-27 추가)**
- 매칭 확정(confirmed) 순간, 지원자 목록에서 "매칭 확정"을 누른 소유자에게는 그 지원자의 회사명/이메일/연락처를 담은 "매칭이 확정됐습니다. 연락해 보세요" 팝업이 자동으로 뜸 — 값은 지원 시점에 지원서(`ProjectApplication.applicantName/email/phone`)에 스냅샷으로 저장돼 있던 걸 그대로 사용(추가 조회 없음)
- 확정된 지원 건은 지원자 목록/내가 한 지원 양쪽 모두 "협의 하기" 버튼이 연락처 아이콘(`Contact`)의 "연락처 열람" 버튼으로 바뀌어, 이후 언제든 다시 눌러서 상대 연락처를 볼 수 있음
- **지원자 쪽에서 보는 프로젝트 소유자의 이메일/연락처는 확정 전에는 절대 노출되지 않음** — `getMyApplications`(`GET /partner/applications/me`)가 지원서 상태가 `confirmed`가 아니면 응답에서 `projectId.ownerId.email`/`companyInfo.phone`/`contactPerson`을 서버에서 지워서 내려보냄. 반대 방향(지원자의 연락처를 소유자가 보는 것)은 지원 시점에 이미 지원서에 스냅샷된 정보라 예전부터 상태와 무관하게 노출되어 있었음(변경 없음)
- "내가 한 지원"에서 매칭이 확정되면 프로젝트명 옆에 "매칭을 축하드립니다!" 배지(2줄, NEW 배지와 같은 스타일)가 뜨고, 한 번 보면 다시 안 뜸(`partnerApplicationConfirmedSeen:{partnerId}` localStorage 키로 seen 처리)

**데이터 모델 및 안읽음 계산**
- 데이터 모델: `PartnerMessage`(개별 메시지, `rootId`로 대화를 묶음) + `PartnerMessageThread`(대화별 상태 문서, `rootId` 기준 1개) — "협의 하기"로 메시지를 보낼 때마다 매번 새 `rootId`(자기참조)로 독립된 대화가 시작됨
- 편지함 UI는 없어졌지만 `GET /partner/messages/received`(`getReceivedMessages`, `isOutgoing`으로 내가 보낸 것도 구분해서 반환)는 여전히 호출됨 — 그 상대와 주고받은 **모든** 메시지(여러 rootId 통합, 발신 방향 무관)를 받아와 두 가지 계산에만 씀:
  1. `mailButtonState.ts`의 `getMailButtonState`가 상대별 마지막 발신자를 판단해 "협의 하기" 버튼의 우편 아이콘(Mail/MailCheck/MailOpen) 결정
  2. 지원자 목록·내가 한 지원 탭과 "프로젝트 활동" 사이드바 뱃지의 안읽음 점(`hasUnreadFromApplicants`/`hasUnreadFromOwners`/`hasUnreadMessage`) 계산 — 상대가 보낸 메시지 중 아직 "본 것"(`partnerMessageCardSeen:{partnerId}` localStorage)으로 표시 안 된 게 있으면 켜짐. **상대방이 보낸** 메시지만 기준으로 계산됨(내가 보낸 메시지는 스스로에게 안읽음을 띄우지 않음)
- 대화(rootId) 상태 값(`open`/`closed`/`deleted`)은 스키마에 남아있지만, 이를 바꾸는 "대화 종료/복원/완전삭제" 기능은 UI에서 폐지됨 — 지금은 도달할 화면이 없어 사실상 모든 대화가 `open` 상태로만 존재함
- (레거시, 정리 대상) 대화 종료/복원/완전삭제 API(`POST /partner/messages/thread/:rootId/close|restore|delete`, 프론트 `partnerService.closeMessageThread`/`restoreMessageThread`/`deleteMessageThread`)와 예전 답장 API(`replyToMessage`, `POST /partner/messages/:messageId/reply`)는 "받은 메시지" 탭이 있던 시절의 기능으로, 백엔드/서비스 레이어에는 그대로 남아있지만 지금은 어떤 화면에서도 호출하지 않는 죽은 코드

## 10. 알림 규칙

### 10.1 알림 타입

| 타입 | 설명 |
|------|------|
| `system` | 시스템 알림 (정지, 해제 등 자동 발송 포함) |
| `notice` | 공지 알림 |
| `publishing` | 퍼블리싱 관련 |
| `comment` | 댓글 알림 |
| `follow` | 팔로우 알림 |
| `proposal` | 제안 알림 |

### 10.2 자동 알림 발송 케이스

| 상황 | 타입 | 설명 |
|------|------|------|
| 계정 정지 | `system` | 정지 범위, 기간 포함 |
| 계정 정지 해제 | `system` | 해제 안내 |
| 파트너 라운지 메시지 수신 (2026-07-27 추가) | `proposal` | 지원 건에 "협의 하기"로 메시지를 보내면 수신자에게 발송 ("파트너 라운지 새 메시지 도착", `sendApplicationMessage`) |
| 매칭 확정 (2026-07-27 추가) | `proposal` | 프로젝트 소유자가 지원자를 확정 처리하면 그 지원자에게 발송 ("매칭이 확정되었습니다", `updateApplicationStatus`) |

### 10.3 관리자 수동 알림 발송 권한

- 발송 가능: `normal` 이상 (super, normal만 가능, monitor는 불가 — 2026-09-09 변경, [[3.3]] 참고)
- 전체 발송(`broadcast=true`): 전체 사용자에게 발송
- 특정 사용자(`userIds`): 지정 사용자에게만 발송

### 10.4 알림 클릭 동작

- `linkUrl`이 있는 경우: 클릭 시 해당 URL로 이동 (`window.location.href`)
- `linkUrl`이 없는 경우: 읽음 처리만 됨
- 실시간 전달: **Socket.IO** (`new-notification` 이벤트)

## 11. 문의하기 (1:1 문의 티켓)

> 2026-09-08 추가. 개발사/파트너/플레이어가 관리자에게 1:1로 문의를 보내는 기능. 마이페이지 "문의하기" 탭에서 시작, 관리자는 `/admin/inquiries`(관리자 포털 "문의하기 관리")에서 전체 문의를 한 화면에서 응대한다.

### 11.1 문의 대상 & 진입점

- 문의는 항상 **관리자 앞으로만** 간다 — 유저끼리는 서로 DM할 수 없다 (`targetUserId`를 지정해도 서버가 무시하고 항상 관리자로 연결).
- 관리자가 여러 명이어도 문의는 **가장 먼저 생성된 관리자 계정**을 대표로 연결하지만, 조회/답장은 관리자 역할이면 누구나 가능 (공용 인박스).
- 진입점: 개발사/파트너 마이페이지(`CorporateMyPage.tsx`), 플레이어 마이페이지(`PlayerMyPage.tsx`)의 "문의하기" 탭. 관리자 마이페이지에는 없음 (관리자는 받는 쪽이라 문의할 대상이 없음).

### 11.2 새 문의 = 매번 새 스레드

- "새 문의"를 누를 때마다 **기존 방을 재사용하지 않고 항상 새로운 문의 스레드를 생성**한다 (고객센터 티켓 방식) — 과거처럼 유저당 방 1개로 묶이지 않는다.
- 새 문의 작성 시 입력: 카테고리, 제목, 내용, 참조 이미지(선택, 1장).
- 참조 이미지는 **문의를 처음 만들 때만** 첨부할 수 있다. 이후 답장을 주고받는 채팅에는 이미지 첨부 기능이 없다 (텍스트만).

### 11.3 카테고리

| 값 | 라벨 |
|---|---|
| `game` | 게임 |
| `account` | 계정 |
| `bug` | 버그 |
| `report` | 신고 |
| `community` | 커뮤니티 |
| `other` | 기타 |

### 11.4 상태 흐름

| 상태 | 값 | 전환 조건 |
|---|---|---|
| 오픈 | `open` | 문의 생성 시 기본값 |
| 진행 중 | `in_progress` | 관리자가 해당 문의에 **처음 답장**하면 서버가 자동 전환 |
| 문의 종료 | `closed` | 관리자가 "문의 닫기" 버튼으로 수동 전환 (유저는 종료 불가) |

- **종료된 문의는 양쪽 다 메시지를 보낼 수 없다** (유저·관리자 모두 입력창 대신 "종료된 문의입니다" 안내만 표시).
- 종료를 되돌리는(재오픈) 기능은 없다.

### 11.5 삭제

- 유저가 목록에서 삭제하면 **본인 목록에서만 숨겨진다** (soft delete). 관리자는 삭제 여부와 무관하게 항상 조회 가능 — 문의 기록은 관리자 쪽에서 영구 보관된다.

### 11.6 안읽음 표시

- 마이페이지 "문의하기" 탭, 관리자 사이드바 "문의하기 관리" 탭에 안읽은 메시지가 있으면 빨간 점이 표시된다.
- 실시간 갱신이 아니라 **페이지 진입/이동 시점에 1회 조회**하는 방식이다 (소켓 연결 없음).

### 11.7 관리자 문의함 필터

- `/admin/inquiries`에서 **상태 / 카테고리 / 유저 타입** 3개 드롭다운으로 필터링 가능.
- 유저 타입은 3가지로 분류: 개발사 / 파트너 / 플레이어.
  - `role === 'player'` → 플레이어
  - `role === 'developer'`이고 `companyInfo.companyCategory === 'developer'` → 개발사, `'partner'` → 파트너 (없으면 `companyType`에 `'developer'` 포함 여부로 판별)
