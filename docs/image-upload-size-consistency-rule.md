# 이미지 업로드 최소 크기 ↔ 실제 노출 크기 동기화 규칙

## 규칙

게임 관련 이미지(아이콘/히어로 배너/스크린샷/서브아이콘)와 관리자 배너 이미지는 **업로드 시 강제하는 "기준 크기(px)"**와 **실제 사이트에 노출되는 화면의 CSS 크기/비율**이 항상 서로 맞아야 한다.

- **2026-09-16부터: 정확히 일치(exact match)가 아니라 "최소 크기(이상)" 검증으로 전환.** 업로드한 이미지의 가로/세로가 기준 크기 이상이면 통과, 하나라도 기준보다 작으면 등록 차단. 기준보다 큰 이미지는 허용(다만 비율이 크게 다르면 `object-cover`로 더 많이 크롭될 수 있음 — 크롭은 화질 저하가 아니라 구도 문제라 별개 사안).
- **노출 화면(디자인) 쪽을 조정하면** → 업로드 기준 크기도 같이 맞춰서 수정한다 (`apps/web/src/lib/imageDimensions.ts`의 `meetsMinSize`/`sizeMismatchMessage`, `ICON_SIZE`/`BANNER_SIZE`/`SCREENSHOT_SIZE`/`SUB_ICON_SIZE` 상수, `AdminCommunityPage.tsx`의 `requiredSize` prop)
- **2026-09-16, 게임관리(`GameDetailManagementPage.tsx`) 미디어 탭 5개 업로드 카드(게임 아이콘/서브아이콘/히어로 배너/트레일러/스크린샷)와 베타존 "기본 정보" 탭에 중복 구현돼 있던 히어로 배너 안내 카드 문구를 단계적으로 정리.** 최종 상태: ① 요건 문구 앞에 붙어있던 별도 설명 줄 제거(예: "게임 카드/목록에 쓰이는 대표 아이콘으로 필수 1개 등록 필요"), ② "· 최대 용량 ...MB" 부분도 제거, ③ 파란 배경(`bg-blue-500/10`) 카드 박스 자체도 제거하고 일반 텍스트(`<p>`)만 남김. 최종 문구 형태(2026-09-16, "이상" 단어도 전부 삭제 반영): "최소 크기 WxHpx · 등록 가능 파일 PNG, JPG, WEBP"(트레일러는 "등록 가능 파일 MP4, MOV, WEBM · 최소 1개 등록", 스크린샷은 "...· 최소 4개 등록"). 검증 로직(`meetsMinSize`)과 실제 차단 동작은 변경 없음 — 화면에 노출되는 안내 텍스트/스타일만 정리한 것.
- **사용자가 "각 카드 텍스트 쪽 적용해"라고 하면, 이 미디어 탭 카드들(현재 5개 + 베타존 중복 아이콘/히어로 배너)의 안내 문구 전부에 동일하게 적용한다 — 묻지 않고.** (2026-09-16 사용자 지시)
- **업로드 기준 크기 쪽을 조정하면** → 실제 노출 화면의 CSS(높이/비율/object-fit 등)도 같이 맞춰서 수정한다
- 사용자가 "이 화면만 따로 할게" 등으로 예외 지정하지 않는 한, **묻지 않고 양쪽을 함께 수정**한다 (2026-09-15 사용자 지시)
- **예외: 프로필 사진(아바타) 업로드는 이 규칙 대상이 아니다.** 자유로운 크기로 업로드 가능하도록 유지한다 (2026-09-15, "이모티콘은 자유롭게 올리게 하고" 요청)
- **이미지 비율(가로:세로) 절대 변경 금지 (2026-09-16 사용자 지시, 같은 날 실수로 한 번 위반해서 규칙 범위를 명확히 확장함).** 두 가지를 다 지켜야 한다:
  1. 리사이징이든 업로드 요구 크기(px) 조정이든, 이미지 관련 작업을 할 때 원본의 가로세로 비율 자체를 바꾸는 일은 절대 하지 않는다. 크기를 줄이거나 늘리는 건 되지만 반드시 기존 비율을 유지한 채로만 한다.
  2. **화면에 그 이미지를 보여주는 박스(컨테이너)의 비율도 항상 원본/업로드 비율과 일치해야 한다.** 높이/폭 등 레이아웃을 조정하다가 박스 비율만 슬쩍 달라지는 것도 위반이다 — `object-cover`라 찌그러짐(stretch)은 없지만, 원본과 다른 비율의 박스에 넣으면 의도치 않게 과하게 크롭된다. 레이아웃 치수를 바꿀 일이 생기면, 이미지가 들어가는 박스만큼은 항상 정확한 비율을 유지하도록 별도로 계산해서 맞춘다(필요하면 이미지 표시 영역을 `aspect-square`/`aspect-[W/H]` 등으로 명시적으로 고정하고, 남는 공간은 레터박스로 남긴다 — 아래 "위반 사례 및 수정" 참고).
  - **사용자가 이후 "비율을 바꿔라"라고 요청하면, 비율을 변경하지 않기로 이미 정했다는 것을 먼저 알린다.**

### 위반 사례 및 수정 (2026-09-16)

- **베타존 참가자 모집 카드 아이콘 비율 위반 발생 → 당일 수정.** "베타존 참가자 모집 패널 높이 20% 축소" 작업 때, 하단 정보 박스(이름/참여인원)는 고정 높이라 안 줄고 그 위 이미지 표시 영역만 254×254(정사각형) → 254×168(1.51:1)로 찌그러지듯 비율이 달라짐 — 원본(게임 아이콘, 450×450 정사각형)과 표시 박스 비율이 어긋난 상태로 방치됐던 걸 사용자가 지적함.
  - **1차 수정(레터박스, 반려됨)**: 카드 이미지 wrapper에 `aspect-square self-center`를 추가해 168×168 정사각형을 만들고 카드 폭(256px)은 그대로 둔 채 좌우 여백(레터박스)으로 가운데 정렬 — 비율 자체는 정확해졌지만 사용자가 "완성도 낮고 저급해 보인다"고 반려함(빈 여백이 어색해 보임).
  - **최종 수정**: 레터박스 대신 **카드 폭 자체를 이미지 정사각형 크기에 맞춰 축소**. `w-64`(256px) → `w-[162px]`로 줄이고, 이미지 wrapper는 다시 `relative flex-1 min-h-0`(레터박스 클래스 제거)로 되돌림 — 카드가 좁아진 만큼 이미지가 폭 전체를 꽉 채우면서 자연스럽게 정사각형이 됨. 카드가 좁아진 대신 한 화면에 보이는 카드 수가 3개→4개로 늘어남(사용자가 "4번째 카드 짤려도 된다"고 이미 허용). 패널 전체 높이(345px)는 변경 없음.
  - **추가 발견 및 수정**: "이미지 높이가 카드마다 다르다"는 지적으로 재확인해보니, 하단 정보 박스(제목/날짜/참여인원/버튼)가 `flex-shrink-0`(콘텐츠 높이만큼만 차지)라서 **마감임박(굵은 빨간 글씨) 카드는 참여인원 텍스트가 줄바꿈되면서 정보 박스가 더 커지고, 그만큼 이미지 영역(`flex-1`)이 눌려서 카드별로 이미지 높이가 미묘하게 달라지는 문제**가 있었음(160×160.45 vs 160×144.45). 1차로 정보 박스에 `h-[104px] overflow-hidden` + 텍스트 `truncate` 처리로 임시 해결.
  - **최최종 수정 (2026-09-16, "카드 높이가 사진/텍스트에 따라 절대 조정되지 않게" 요청 반영)**: 이미지·정보 박스·카드·패널 전부를 **`flex-1`/`h-full` 등 콘텐츠 의존형 크기 계산을 완전히 제거하고, 전부 하드코딩된 고정 px 값**으로 전환. 이미지 `h-[160px]`(고정, 절대 안 변함), 정보 박스 `h-[128px] overflow-hidden`(제목 1줄/날짜 1줄/참여인원 1줄/버튼 1줄 — 참여인원 옆에 있던 버튼을 참여인원 아래 줄로 이동), 카드 전체 `h-[288px]`(=160+128), 패널(`베타존 참가자 모집` 박스) `h-[367px]`(=288+헤더/패딩 오버헤드 79px). 제목은 기존대로 `truncate`로 길면 말줄임 처리. 이제 어떤 텍스트 길이·마감임박 여부·이미지 내용과도 무관하게 모든 치수가 항상 고정값 — 콘텐츠에 따라 흔들리는 지점이 구조적으로 없음.
  - **연쇄 반영**: 베타존 참가자 모집 패널이 `367px`로 커지면서 `items-stretch`로 옆에 붙어있는 "인기글/공지" 패널(`CommunityHotCard`)도 같이 늘어났는데, 5개 항목 목록(`gap-0.5`=2px 간격)은 그대로라 마지막 항목 아래로 빈 공간이 남는 문제가 생김 → 사용자가 "게시물마다 간격을 벌려서 마지막 텍스트가 패널 하단까지 오게" 요청. 목록 컨테이너(`MainPage.tsx` `CommunityHotCard`, 318번째 줄 근처) 간격을 `gap-0.5`(2px) → `gap-[9.65px]`로 조정(실측 가용 높이 299px, 항목 5개×52.08px, 간격 4칸에 남는 여백을 균등 분배해서 역산한 값) — 마지막 항목이 패널 하단과 정확히 일치(오차 0.05px).

## 이미지 슬롯 전용 원본 규칙 (2026-09-15 사용자 지시)

- **이미지 슬롯(아이콘/히어로 배너/스크린샷/관리자 배너 각 탭)마다 그 슬롯 전용으로 업로드된 원본 이미지만 쓴다.** 하나의 이미지를 리사이즈/크롭/조정해서 다른 슬롯에 재사용하지 않는다 (예: 히어로 배너용으로 올린 1920×640 이미지를 크롭해서 512×512 아이콘으로 다시 쓰는 식의 작업 금지).
- **사용자가 "이 이미지 조정해서 다른 슬롯에도 써" 같은 방식으로 요청하면, 작업 전에 이 규칙이 있다는 것을 터미널에 먼저 알린다** (자동으로 조용히 따르지 않고, 규칙 존재를 알린 뒤 사용자 확인을 받는다).

### 히어로 배너 최소 크기 축소 시도 및 재상향 (2026-09-17)

## 업로드 요구 크기 재산정 — "실제 표시 크기 2배 여유" (2026-09-16)

**배경**: 서버 리사이징 파이프라인이 없어서(아래 "알려진 한계" 참고) 업로드된 원본이 그대로 서빙된다. 그런데 여러 이미지가 실제 화면에 표시되는 크기(px)보다 훨씬 큰 최소 크기를 요구하고 있어서, 표시 크기 대비 원본이 과도하게 커 대역폭을 낭비하고 있었다(예: 게임 아이콘 512×512 요구인데 실제 최대 표시는 라이브존 카드 기준 172~222px). 리사이징 파이프라인을 새로 만드는 대신, **업로드 요구 크기를 "실제 화면에서 가장 크게 쓰이는 곳의 표시 크기 × 2(레티나 디스플레이 대응 여유)"로 낮추는 방법**으로 1차 대응함.

**원칙**:
- 각 이미지 필드가 쓰이는 모든 위치를 찾아 실측 후, 그중 가장 큰 표시 크기를 기준으로 삼는다(뷰포트 1440px/1920px 두 군데에서 측정 — 반응형인 경우 더 큰 값 채택).
- 새 요구 크기 = 그 최댓값 × 2, 단 **기존 비율은 절대 유지**(위 "이미지 비율 절대 변경 금지" 규칙).
- **풀와이드 히어로/배경용 이미지(히어로 배너, 메인_배너, 커뮤니티_배너)는 이 계산에서 제외**했다 — 화면을 꽉 채우는 용도라 이미 큰 뷰포트 기준으로 적정하고, 여기에 기계적으로 2배를 적용하면 오히려 요구 크기가 더 커져서(예: 히어로 배너는 1440 실측×2=2880 > 현재 1920) 대역폭 절감이라는 원래 목적에 역행한다.

## 메인_추천게임 배너 — 노출 크기 확정 진행 상황 (SUPERSEDED — 2026-09-16 게임 선택형으로 전환하며 종료)

이 절은 "직접 이미지 업로드" 방식이었을 때의 진행 기록이다. 같은 날 안에 사용자가 **"이미지 등록이 아니라 관리자 배너에서 게임을 등록하면 히어로 배너가 나오게 해달라"**고 요청해서, 아래에서 진행하던 "노출 크기 먼저 확정 → 업로드 요구 크기 나중에 결정" 절차 자체가 필요 없어졌다 — 이제 업로드가 없고 게임의 기존 히어로 배너(1920×823, 21:9)를 그대로 재사용하기 때문이다.

- **컨테이너(추천 게임 섹션) 폭**: `w-full`, 실측 1151px — 우측 끝이 "베타존 참가자 모집" 패널이 아니라 **우측 카테고리/공지 패널(메인공지·게임공지·베타공지·인기글, `CommunityHotCard`)의 우측 끝과 정확히 일치**하도록 고정(1295.5px 지점). 이 폭은 계속 유지.
- **우측 카테고리 패널 폭**: 331.48px(고정, 손 안 댐) — 참고용 기준치.
- **실제 이미지(슬라이드) 폭**: `REC_SLIDE_WIDTH_PCT` 상수로 조절, 컨테이너 폭에 대한 비율. 73.6%(847.1px, 컨테이너 폭 대비 이미지 좌우만 20% 축소)로 유지. 높이는 고정값(`REC_BIG_HEIGHT`) 대신 **`aspect-[21/9]`로 전환**해서 히어로 배너 원본 비율(1920:823)과 항상 정확히 일치하도록 함.

## 기능 변경 이력 — 메인_추천_소형 완전 제거 (2026-09-16)

사용자 지시로 "추천 게임" 섹션의 우측 30% 소형 배너 스택(무작위 3개 노출)을 완전히 제거하고, 좌측 70% 대형 배너를 전체 폭으로 넓혀 "추천 게임" 섹션 전체를 이것 하나로 통일함. 정리한 범위:

- **프론트엔드**: `MainPage.tsx`에서 `RecommendMiniStack`/`BannerCell` 컴포넌트, `REC_MINI_GAP`/`REC_MINI_HEIGHT` 상수, `recommendMiniBanners` state, `getMiniRecommendBanners()` 호출 전부 삭제. "추천 게임" 섹션은 `<RecommendBigBanner>` 하나만 전체 폭으로 렌더링.
- **관리자 배너 관리**: `AdminCommunityPage.tsx`에서 "메인_추천_소형" 탭(및 관련 state 8개, 핸들러 4개, `loadRecommendMini`)을 통째로 제거. "메인_추천_대형" 탭은 라벨/타이틀에서 "(대형)" 표기를 떼고 "메인_추천게임"으로 통일(더 이상 "소형"과 구분할 필요가 없어짐).
- **서비스/백엔드**: `adminService.ts`의 `getMiniRecommendBanners`/`getAllMiniRecommendBanners`/`uploadMiniRecommendBanner` 삭제, `CommunityBanner`의 `position` 타입에서 `'recommendmini'` 제거(프론트 타입 + `packages/db` Mongoose 스키마 enum + `communityBannerController.ts`의 `allowed` 배열 전부). 신규 `recommendmini` 배너 업로드는 이제 API 레벨에서부터 막힘.

## 기능 변경 이력 — 메인_추천게임 배너를 이미지 업로드 → 게임 선택형으로 전환 (2026-09-16)

"메인_베타존참가자모집" 배너와 동일한 패턴(게임 선택 → 그 게임의 기존 이미지 자동 재사용)을 "메인_추천게임"에도 적용. 차이는 재사용하는 필드 — 베타존참가자모집은 `Game.thumbnail`(아이콘), 추천게임은 **`Game.bannerImage`(히어로 배너)**.

- **백엔드**(`communityBannerController.ts`): `uploadCommunityBanner`/`updateCommunityBanner`에 `position === 'recommend'` 분기 추가 — `linkUrl`에서 게임 id를 뽑아 `Game.bannerImage`를 조회해서 그대로 `imageUrl`로 사용, 없으면 400. 게임을 바꿔서 수정할 때도 새 게임의 `bannerImage`로 다시 동기화됨.
- **프론트 서비스**(`adminService.ts`): `uploadRecommendBanner`를 `(file, extra)` → `(linkUrl, extra)`로 변경 — 더 이상 이미지 파일을 보내지 않음.
- **관리자 화면**(`AdminCommunityPage.tsx`): `BannerSection`의 기존 `gameHeroBanner` 모드(이미지 업로드 UI 숨기고 게임 선택기만 노출)를 그대로 재사용. 다만 안내 문구가 "아이콘"으로 하드코딩돼 있던 걸 `gameHeroBannerLabel` prop으로 분리해서 추천게임 탭엔 "히어로 배너"로 표시되게 함. `handleRecommendAdd`도 파일 필수 검증 → `linkUrl` 필수 검증으로 변경.
- **메인 화면**(`MainPage.tsx` `RecommendBigBanner`): 위 "노출 크기 확정 진행 상황" 항목 참고 — 슬라이드 박스를 `aspect-[21/9]`로 전환.
- **참고**: `adminService.ts`의 `uploadNewGameBanner` 주석이 실제로는 `Game.thumbnail`을 쓰면서 "히어로 배너(Game.bannerImage)"라고 잘못 남아있던 걸 이번에 같이 바로잡음(코드 동작 자체는 원래도 정상이었음, 주석만 stale했던 것).
- **⚠️ 부작용**: DB에 기존 `position: 'recommendmini'` 문서 **5개**가 남아있음 — 삭제하지 않고 그대로 둠(고아 데이터, 어디서도 조회/노출/관리 안 되니 무해하지만 완전히 지우고 싶으면 별도로 요청할 것).
